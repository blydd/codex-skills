## 第 1 题　HTML / CSS：像素级还原与移动端适配

**问题**：
1. 设计稿按 750px 宽出图，里面一个按钮标注「宽 200px、高 88px、字号 32px」。你在代码里**具体怎么写**，才能让它在窄屏手机和宽屏安卓机上**占屏幕的比例一致**？说清方案和换算关系。
2. 设计师验收时说「你这条 `border-top: 1px` 的分割线在手机上看着太粗」。**为什么 1px 在高清屏上会变粗**，你通常怎么解决？
3. 一个父 div 里放了三个 `float: left` 的子元素，结果**父 div 高度是 0、背景色完全看不见**；另外父 div 和上方元素之间本该间隔 40px，实际只隔了 20px。**这两个现象分别是什么原因、怎么解决**？

<details>
<summary>标准参考答案</summary>
<p><strong>问题1（750 稿适配与换算）</strong>：核心是「<strong>让元素按屏幕宽度的比例缩放</strong>」，而不是写死 px。两种主流方案：① <strong>rem 方案</strong>——rem 是「相对于 html 根元素 font-size 的单位」，把 html 的 font-size 设成「屏幕宽度 / 7.5」（750 稿下 1rem = 100 设计稿 px），那 200px 写 <code>2rem</code>、32px 写 <code>0.32rem</code>；实际项目用 <code>postcss-pxtorem</code> 在构建时自动换算，你照着设计稿写 px 就行。② <strong>vw 方案（现在更推荐）</strong>——vw 是「屏幕宽度的 1%」，750 稿下 1 设计稿 px = 100/750 = 0.1333vw，所以 200px 写 <code>26.67vw</code>、32px 写 <code>4.27vw</code>，用 <code>postcss-px-to-viewport</code> 自动换算，<strong>不依赖 JS、也不会被根字号影响</strong>。人话对照：这两种方案都等价于后端说的「<strong>按百分比而不是绝对值布局</strong>」，只是换算交给构建工具做。<strong>必须配套的三件事</strong>：全局设 <code>* { box-sizing: border-box }</code>（否则量到 200px 的元素实际占位是 200+padding×2+border×2，这是还原偏差最常见的来源）；移动端必加 <code>&lt;meta name="viewport" content="width=device-width, initial-scale=1"&gt;</code>（不加的话手机会按 980px 的虚拟宽度渲染再整体缩小，字和布局都会变得极小）；1px 边框和字体大小这类<strong>不希望跟着屏幕缩放</strong>的，要在插件里排除转换（写大写 <code>PX</code> 或配 min 值）。</p>
<p><strong>问题2（1px 变粗）</strong>：CSS 里的 1px 是<strong>逻辑像素</strong>，在 dpr=2 或 3 的高清屏（Retina、大部分安卓机）上会被放大成 2~3 个<strong>物理像素</strong>，所以看着粗。三种解法：① <strong>伪元素 + transform 缩放</strong>（兼容性最好、最常用）——用 <code>::after</code> 画一条 1px 的线，再 <code>transform: scaleY(0.5)</code> 压成半个像素；② <code>border: 0.5px</code>（iOS 支持，部分安卓会当成 0 或直接不显示）；③ 用 <code>box-shadow: 0 0.5px 0 #ddd</code> 模拟。</p>
<p><strong>问题3①（父元素高度 0 / 浮动塌陷）</strong>：子元素设了 <code>float</code> 之后会<strong>脱离文档流</strong>，父元素计算高度时就当它不存在，高度变成 0，背景色自然看不见。三种解法：① 给父元素加 <strong>clearfix</strong> 伪元素 <code>::after { content:''; display:block; clear:both }</code>；② 给父元素 <code>overflow: hidden</code> 或 <code>display: flow-root</code> 触发 <strong>BFC</strong>（块级格式化上下文，人话讲就是「一个独立的渲染小房间，房间里的布局不影响外面」）；③ <strong>最推荐：直接用 flex / grid 布局</strong>——现代项目已经不用 float 做布局了，从根上没有这个问题。</p>
<p><strong>问题3②（间距只有 20px / margin 合并）</strong>：这是 <strong>margin 合并（外边距折叠）</strong>——垂直方向上相邻的两个 margin 不会相加，而是<strong>取较大的那个</strong>；父子之间还会出现子元素的 <code>margin-top</code> 「穿透」父元素跑到外面去。解法：给父元素触发 BFC（<code>display: flow-root</code> 或 <code>overflow: hidden</code>）；或只统一用一个方向的外边距（如全用 <code>margin-bottom</code>）；或改用 flex / grid 布局（<strong>flex 容器内部的 margin 不会发生合并</strong>）。</p>
<p><strong>常见坑（真做过还原的才答得出）</strong>：字体族和行高与设计稿不一致导致文字高度对不上（设计稿常用苹方/思源黑体，需要引字体包）；图片按 1 倍图出图在高清屏上发虚（要出二倍图/三倍图）；设计稿没给的状态被漏掉（空数据、加载中、错误提示、超长文本、按钮禁用）；<code>z-index</code> 只在 <code>position</code> 非 static 或 flex 子项上生效，且受父级层叠上下文限制（父级 z-index 低，子元素设 9999 也没用）；<code>img</code> 底部有约 3px 缝隙（inline 元素按基线对齐导致，用 <code>display: block</code> 消除）；flex 子项默认 <code>min-width: auto</code> 会导致长文本撑破容器，要加 <code>min-width: 0</code> 省略号才生效。</p>
<p><strong>判断锚点</strong>：能说清 rem / vw 的换算关系，并主动提到 <code>box-sizing</code> 和 viewport → 中级及以上；只会说「用 rem 适配」但讲不出换算比例和配套设置 → 初级；1px 和浮动塌陷两个问题答不出具体解法 → 移动端经验存疑。</p>
</details>

## 第 2 题　原生 JS：ES6、事件循环与异步

**问题**：
1. 一个页面里同时有同步代码、`setTimeout` 定时器回调、还有 Promise 的 `.then` 回调，**浏览器按什么顺序执行它们**？说下 JS **事件循环**的机制，**宏任务和微任务**分别有哪些？
2. 面试常考的经典场景：一个 for 循环里注册了三个定时器，回调里打印循环变量。**用 `var` 声明循环变量和用 `let` 声明，最终打印的结果有什么不同？为什么**？顺便说说 var 和 let 在**作用域**上的本质区别。
3. 一个列表有 100 行，每行一个「删除」按钮，而且列表数据会不断刷新。**你怎么绑这个点击事件**、为什么这么绑？顺带说下**事件流**的三个阶段。

<details>
<summary>标准参考答案</summary>
<p><strong>问题1（事件循环输出顺序）</strong>：输出 <strong>1 → 4 → 3 → 2</strong>。原理：JS 是<strong>单线程</strong>（同一时间只能干一件事，这是 JS 最初被设计成浏览器脚本语言决定的）。为了不阻塞，JS 用「事件循环」调度，规则是：<strong>一轮事件循环取一个宏任务执行 → 执行完把微任务队列整个清空 → 浏览器判断要不要渲染 → 取下一个宏任务</strong>。<strong>宏任务</strong>：整体 script、setTimeout、setInterval、I/O、UI 渲染、事件回调；<strong>微任务</strong>：Promise.then / catch / finally、async/await 中 await 之后的代码、queueMicrotask、MutationObserver。所以同步的 1 和 4 先打印，然后清空微任务打印 3，最后才轮到宏任务 setTimeout 打印 2。<strong>后端类比</strong>：类似单线程 Reactor 的事件循环——一个线程按队列处理任务，慢任务会阻塞后面所有任务（所以 JS 里不能有长耗时的同步计算，否则页面会「假死」）。</p>
<p><strong>问题2（var vs let 循环，经典题）</strong>：<code>var</code> 版打印 <strong>3 3 3</strong>，<code>let</code> 版打印 <strong>0 1 2</strong>。原因：<code>var</code> 是<strong>函数作用域</strong>，整个循环共用同一个 <code>i</code>，等定时器回调执行时循环早结束了、<code>i</code> 已经变成 3；<code>let</code> 是<strong>块级作用域</strong>，<strong>每次循环都会创建一个新的块级作用域并复制一份 <code>i</code></strong>，所以每个回调记住的是自己那一轮的值。ES6 之前的老写法是用 IIFE（立即执行函数）把当前值存住。这个题能直接看出候选人是否真理解作用域，还是只会用 ES6 语法。</p>
<p><strong>问题3（事件委托）</strong>：正确做法是<strong>事件委托</strong>——把监听器绑在<strong>父容器</strong>上，通过 <code>event.target</code> 判断点的是哪一行，而不是给 100 个按钮各绑一个。写法：<code>list.addEventListener('click', e =&gt; { const btn = e.target.closest('.del'); if (!btn) return; remove(btn.dataset.id) })</code>。两个好处：① 只绑一个监听，内存占用小、绑定开销低；② 列表<strong>动态新增的行不用重新绑事件</strong>（因为事件是从父元素冒泡上来的）。注意 <code>e.target</code> 是真正被点中的最内层元素（可能是按钮里的图标），所以要 <code>closest('.del')</code> 向上找按钮。<strong>事件流三阶段</strong>：一次点击在 DOM 里传播分三步——<strong>捕获</strong>（从 window 一层层往下找到目标元素）、<strong>目标</strong>（到达真正被点中的元素）、<strong>冒泡</strong>（再从目标一层层冒回 window）。<code>addEventListener(type, fn, useCapture)</code> 第三个参数 <code>true</code> 表示在<strong>捕获阶段</strong>触发，<code>false</code>（默认）表示在<strong>冒泡阶段</strong>触发。<code>e.stopPropagation()</code> 阻止继续传播，<code>e.preventDefault()</code> 阻止浏览器默认行为（如 a 标签跳转、表单提交）。补充：<code>focus/blur</code>、<code>scroll</code>、<code>mouseenter/leave</code> 这几个事件<strong>不冒泡</strong>（需要冒泡可用 focusin/focusout）。</p>
<p><strong>常见坑（能答出的是真写过业务）</strong>：<strong>防抖与节流</strong>——防抖是「等你停下来我再做」（最后一次触发后等 n 毫秒执行，期间再触发就重新计时），用于<strong>搜索框输入联想、表单校验、窗口 resize</strong>；节流是「不管你点多快，我按我的节奏来」（n 毫秒内无论触发多少次只执行一次），用于<strong>滚动监听、按钮防连点、埋点上报</strong>。手写防抖：<code>function debounce(fn, delay = 300) { let timer = null; return function (...args) { clearTimeout(timer); timer = setTimeout(() =&gt; fn.apply(this, args), delay) } }</code>——能写出来并说明 <code>apply</code> 是为了把 this 和参数传回原函数 → 加分。<strong>深浅拷贝</strong>：<code>JSON.parse(JSON.stringify(obj))</code> 会<strong>丢掉</strong> undefined、函数、Symbol，Date 变字符串，RegExp / Map / Set 变空对象，<strong>循环引用直接报错</strong>；现代浏览器用 <code>structuredClone(obj)</code>（支持循环引用，但不拷函数）。<strong>this 绑定</strong>：只针对普通函数，<code>obj.fn()</code> 时 this 指向 obj（谁调用指向谁）、<code>call/apply/bind</code> 可强制指定、<code>new</code> 指向新对象；<strong>箭头函数没有自己的 this</strong>，沿作用域链继承外层，且 call/apply/bind 改不了。最常见的坑：把对象方法当回调传出去（<code>const f = obj.fn; f()</code>）就丢了 this。</p>
<p><strong>判断锚点</strong>：事件循环输出顺序答对且能说清「微任务先于下一个宏任务」→ 合格；能说出 <code>await</code> 后面的代码等价于 <code>.then()</code> 回调（也是微任务）→ 加分；var/let 讲不出「每次循环创建新块级作用域」、只会说「let 更好」→ 基础不牢。</p>
</details>

## 第 3 题　浏览器渲染、HTTP 缓存与上线后的性能问题

**问题**：
1. 用户反馈「页面**第一次打开很慢、第二次打开就快了**」，你觉得最可能的原因是什么？讲讲 **HTTP 强缓存和协商缓存**的区别，以及相关请求头 / 响应头怎么写的。
2. 你们**发版之后**，有用户反馈「看到的还是旧页面」，还有用户反馈「页面白屏」，分别可能是什么原因（结合浏览器缓存和前端路由说）？前端这边怎么避免？
3. 页面上有个元素要频繁改样式：改 `width`、改 `background-color`、改 `transform`，**三者对浏览器的开销有什么不同**？写代码时怎么减少这类开销？

<details>
<summary>标准参考答案</summary>
<p><strong>问题1（第一次慢第二次快 / HTTP 缓存）</strong>：最常见的原因是<strong>命中了浏览器缓存</strong>。第一次请求时服务器在响应头里下发缓存规则，浏览器把资源存到本地，第二次就可能直接读本地副本。<strong>强缓存</strong>：<code>Cache-Control: max-age=3600</code> 表示 3600 秒内<strong>直接读本地副本、完全不发请求</strong>（DevTools 里显示 200 from memory/disk cache）；<code>no-cache</code> 表示「可以存，但每次都要问服务器」；<code>no-store</code> 表示「完全不许存」（敏感数据用）。老字段 <code>Expires</code> 是绝对时间、受本地时钟影响，<strong>优先级低于 Cache-Control</strong>。<strong>协商缓存</strong>：强缓存过期后，请求带上 <code>If-None-Match: 上次的ETag</code> 或 <code>If-Modified-Since: 上次的Last-Modified</code> 去问服务器，内容没变服务器返回 <strong>304 Not Modified</strong>（不带响应体，浏览器继续用本地副本），变了才返回 200 + 新内容。<strong>ETag 优先级高于 Last-Modified</strong>，因为它能感知「内容没变但修改时间变了」，而 Last-Modified 只有秒级精度。<strong>后端类比</strong>：就是本地缓存 + ETag/版本号校验——命中直接用，过期带着指纹去问一次。补充：除了缓存，第一次慢也可能是 DNS 解析、TCP/TLS 握手、后端接口慢或 JS 体积过大，要会看 Network 面板的 waterfall 区分。</p>
<p><strong>问题2①（发版后还是旧页面）</strong>：因为 <code>index.html</code> 被<strong>强缓存</strong>了——浏览器拿着旧的 html，里面引用的还是旧版本的 js（新版本的 js 文件名带新 hash，但旧 html 里根本没引用它）。<strong>标准做法</strong>：<code>index.html</code> 设 <code>Cache-Control: no-cache</code>（每次都问服务器），<strong>带 hash 的 js/css 设长缓存</strong>（如 <code>max-age=31536000</code>）——内容变了文件名就变，浏览器自然会去下新的，没变的继续用缓存。这就是「<strong>打包分包 + 长缓存</strong>」这套组合拳，类比后端就是「把不变的依赖单独打成一个 jar，靠版本号/指纹缓存复用」。</p>
<p><strong>问题2②（白屏）</strong>：三个最常见原因——① 用了 <strong>history 路由</strong>，刷新时浏览器真的去请求 <code>/user/1</code>，服务器上没有这个路径就返回 404（hash 模式 URL 带 <code>#</code>，<code>#</code> 后面的变化不会发给服务器，所以不会 404）；<strong>解法：服务端配 fallback</strong>，Nginx 写 <code>try_files $uri $uri/ /index.html;</code>，把所有路径都返回 index.html 交给前端路由接管。② 部署在子路径（如 <code>/admin/</code>）但 <code>base</code>（webpack 里叫 <code>publicPath</code>）没配，静态资源全 404。③ JS 报错（兼容性问题、依赖缺失）导致渲染中断。排查顺序：先看 Network 面板有没有 404，再看 Console 有没有报错。</p>
<p><strong>问题3（width / background-color / transform 的开销）</strong>：改 <strong>width</strong>（以及位置、字体大小、增删 DOM）会影响几何尺寸 → 浏览器要重新计算布局，叫<strong>重排 / 回流（Reflow）</strong>，重排之后一定触发重绘，<strong>最贵</strong>；只改 <strong>background-color</strong>（以及颜色、阴影）不影响布局 → 跳过布局直接重新画，叫<strong>重绘（Repaint）</strong>，较便宜；只改 <strong>transform</strong> 和 <strong>opacity</strong> → 连重绘都跳过，直接走 <strong>GPU 合成层</strong>，<strong>最便宜</strong>（所以做动画优先用 transform / opacity，必要时加 <code>will-change: transform</code> 提示浏览器提前提层）。<strong>怎么减少</strong>：① <strong>批量修改</strong>——用 <code>DocumentFragment</code>（内存里的临时容器，改完一次性插入页面），或先 <code>display: none</code> 改完再显示，或用 class 一次性切换样式；② <strong>读写分离（最重要）</strong>——不要在循环里「写完样式又读 <code>offsetHeight</code> / <code>scrollTop</code> / <code>getBoundingClientRect()</code>」，因为<strong>读取会强制浏览器立刻刷新布局</strong>（强制同步布局），正确做法是<strong>先把要读的一次性读完，再统一写</strong>；③ 动画元素用 <code>position: absolute/fixed</code> 脱离文档流，避免影响别人；④ 长列表用虚拟滚动，减少 DOM 数量。</p>
<p><strong>常见坑与延伸</strong>：<strong>script 的 defer / async</strong>——普通 <code>&lt;script src&gt;</code> 会<strong>阻塞 DOM 解析</strong>；<code>async</code> 下载不阻塞但<strong>下载完立刻执行</strong>、多个 async 脚本<strong>执行顺序不保证</strong>（适合统计、广告这类独立脚本）；<code>defer</code> 下载不阻塞且<strong>等 DOM 解析完成后按序执行</strong>（最常用，等价于把 script 放到 body 底部）。<strong>常见状态码</strong>：301 永久重定向（浏览器会缓存，换域名用）、302 临时重定向（未登录跳登录）、<strong>304 命中协商缓存</strong>、<strong>401 未认证</strong>（没登录 / token 无效）、<strong>403 已认证但没权限</strong>、<strong>502 Bad Gateway</strong>（网关收到上游无效响应，常见原因是后端服务挂了）、<strong>504 Gateway Timeout</strong>（网关等上游超时，常见原因是后端接口太慢）——前端排查时 4xx 先查自己的请求，5xx 找后端。</p>
<p><strong>判断锚点</strong>：能讲清「index.html 设 no-cache + 带 hash 资源设长缓存」这套组合拳 → 真上过线；只说「让用户清一下缓存」→ 没系统处理过发布问题；能说出 history 路由要配 Nginx fallback → 分层明显加分。</p>
</details>

## 第 4 题　网络请求：Ajax、跨域与请求头

**问题**：
1. 不用任何库，用浏览器原生 **XMLHttpRequest 发一个 POST 请求**，**整个流程分哪几步**、有哪些关键点（请求头什么时候设置、超时和网络错误怎么处理、响应怎么解析）？再说下 `fetch` 和 XHR 相比有哪几个**必须知道的差别**？
2. 前端调后端接口，控制台报 `No 'Access-Control-Allow-Origin' header`，**这是什么原因**（请求到底有没有发到后端）？你项目里**怎么解决跨域**的，CORS / 开发代理 / Nginx 反向代理各自适用什么场景？
3. 请求头 `Content-Type` 有哪几种常见取值、分别对应什么数据格式？**文件上传**时用什么、为什么**不要手动设置**它？

<details>
<summary>标准参考答案</summary>
<p><strong>问题1（手写原生 Ajax）</strong>：
<pre><code>function request({ url, method = 'GET', data = null, headers = {}, timeout = 10000 }) {
  return new Promise((resolve, reject) =&gt; {
    const xhr = new XMLHttpRequest()
    xhr.open(method, url, true)          // 第三个参数 true = 异步
    xhr.timeout = timeout                // 超时时间（毫秒）
    xhr.setRequestHeader('Content-Type', 'application/json')
    Object.entries(headers).forEach(([k, v]) =&gt; xhr.setRequestHeader(k, v))
    xhr.onreadystatechange = () =&gt; {
      if (xhr.readyState !== 4) return   // 4 = DONE，请求完成
      if (xhr.status &gt;= 200 &amp;&amp; xhr.status &lt; 300) {
        try { resolve(JSON.parse(xhr.responseText)) } catch { resolve(xhr.responseText) }
      } else {
        reject(new Error('HTTP ' + xhr.status))
      }
    }
    xhr.ontimeout = () =&gt; reject(new Error('请求超时'))
    xhr.onerror = () =&gt; reject(new Error('网络错误'))   // 断网、DNS 失败等
    xhr.send(data ? JSON.stringify(data) : null)
  })
}</code></pre>
关键点：<code>readyState</code> 五档——0 未初始化(UNSENT)、1 已调用 open(OPENED)、2 已收到响应头、3 正在接收响应体、4 完成(DONE)；<code>setRequestHeader</code> 必须在 <code>open</code> 之后、<code>send</code> 之前调用；POST 要 <code>send(字符串)</code>，GET 的参数拼在 URL 上（注意用 <code>encodeURIComponent</code> 转义）。</p>
<p><strong>问题1（fetch 与 XHR 的四个关键差别）</strong>：① <strong>fetch 只有在网络错误时才会 reject，404 / 500 这类 HTTP 错误状态不会 reject</strong>，必须自己判断 <code>res.ok</code>（或 <code>res.status</code>）后手动抛错——这是最常见的 bug 来源；② <strong>fetch 默认不带 Cookie</strong>，跨域要显式写 <code>credentials: 'include'</code>（XHR 对应 <code>xhr.withCredentials = true</code>）；③ <strong>fetch 没有内置超时和上传进度</strong>，超时要用 <code>AbortController</code> + <code>setTimeout</code> 自己实现，上传进度只能用 XHR 的 <code>xhr.upload.onprogress</code>；④ 响应体要 <code>await res.json()</code> 解析，且一个 Response 只能读一次。实际项目里大家用 <strong>axios</strong>（基于 XHR 封装），自带拦截器、超时、进度、自动 JSON 转换，比裸 fetch 好用。</p>
<p><strong>问题2（跨域原因）</strong>：这是浏览器的<strong>同源策略</strong>——「协议 + 域名 + 端口」三者都相同才算同源，非同源的 Ajax 响应会被浏览器拦下来。<strong>关键点（很多人答错）：请求其实已经发到服务器、后端也可能已经处理了，是浏览器拿到响应后把它挡掉了</strong>，所以后端日志里能看到这条请求。<strong>后端类比</strong>：类似网关白名单——不是拦请求，而是拦响应。这是一条安全机制，防止恶意网站拿着你在本站的 Cookie 去访问别的站点。</p>
<p><strong>问题2（三种解法与适用场景）</strong>：① <strong>CORS（跨域资源共享，生产标准做法）</strong>——由服务端在响应头里加 <code>Access-Control-Allow-Origin: https://前端域名</code>、<code>-Allow-Methods</code>、<code>-Allow-Headers</code>（要允许自定义头如 Authorization 时必须写）、<code>-Allow-Credentials: true</code>（允许带 Cookie）。<strong>注意：一旦要带 Cookie，Allow-Origin 就不能写 <code>*</code>，必须写具体域名，否则浏览器直接拒绝。</strong> ② <strong>开发环境代理</strong>——Vite 的 <code>server.proxy</code> / webpack 的 <code>devServer.proxy</code>，前端请求打到同源的本地开发服务器，由它转发给后端（<strong>服务器之间的请求不受同源策略限制</strong>，同源策略只管浏览器），开发期最简单。③ <strong>生产用 Nginx 反向代理</strong>——把 <code>/api/</code> 转发到后端地址，让前后端对外表现为同源，最省事，也是最常见的线上方案。补充：JSONP（利用 <code>&lt;script&gt;</code> 标签不受同源限制，只支持 GET，基本淘汰）、postMessage（iframe 之间通信）、WebSocket（协议本身不受同源策略限制）。</p>
<p><strong>问题3（Content-Type）</strong>：四种常见取值——① <code>application/json</code>：JSON 字符串，<strong>现在前后端分离最常用</strong>；② <code>application/x-www-form-urlencoded</code>：表单默认格式，形如 <code>a=1&amp;b=2</code>；③ <code>multipart/form-data</code>：<strong>文件上传必须用这个</strong>（带 boundary 分段，能同时传文件和字段）；④ <code>text/plain</code>：纯文本。<strong>为什么不要手动设置</strong>：因为浏览器需要自动生成并写上 <strong>boundary</strong>（分隔各段数据的随机字符串），你手动设成 <code>multipart/form-data</code> 却没带 boundary，后端就解析不出文件——所以用了 axios 就直接传 <strong>FormData 对象</strong>，让浏览器自己处理。<strong>常见坑</strong>：Content-Type 写错后端就收不到参数（后端要表单你发了 JSON，或反过来）。</p>
<p><strong>常见坑与延伸</strong>：<strong>预检请求</strong>——只有同时满足「方法是 GET / HEAD / POST」且「请求头只用了 Accept、Accept-Language、Content-Language 和三种简单 Content-Type」才是简单请求、不发预检；其余情况（<strong>PUT / DELETE、<code>Content-Type: application/json</code>、自定义头 Authorization</strong>）都会先发一个 <strong>OPTIONS 预检</strong>去问服务器「我这样请求你允许吗」——很多人以为 OPTIONS 是 bug，其实它是正常流程，服务端设 <code>Access-Control-Max-Age</code> 可缓存预检结果减少往返。<strong>上传进度与取消</strong>：进度用 <code>xhr.upload.onprogress</code>（<strong>注意是 xhr.upload 不是 xhr</strong>，下载进度才用 <code>xhr.onprogress</code>）；取消用 <code>xhr.abort()</code> 或 fetch 的 <code>AbortController</code>，典型场景是切换 tab 时取消上一个未完成的请求，避免结果覆盖。<strong>登录态</strong>：Cookie + Session 方案里 <code>HttpOnly</code> 表示<strong>这个 Cookie 不能被 JS 读取</strong>（防 XSS 盗取）、<code>Secure</code> 只在 HTTPS 下传输、<code>SameSite</code> 防 CSRF；Token 方案里接口返回 401 时配合 refresh token 做<strong>无感刷新</strong>。</p>
<p><strong>判断锚点</strong>：能手写完整 XHR（含超时和 onerror）→ 基础扎实；能说出「请求其实到了后端、是浏览器拦的响应」→ 真解决过跨域；认为跨域只能后端改、不知道开发代理 → 经验偏弱；知道 OPTIONS 是预检而不是 bug → 加分。</p>
</details>

## 第 5 题　Vue 3：响应式原理、Composition API 踩坑与项目配置（重点）

**问题**：
1. 用 `reactive` 声明一个对象，**用解构把某个属性取出来赋给普通变量后修改，页面却不更新**，这是什么原因？再问两个：**`ref` 为什么在 script 里必须写 `.value`**？把 reactive 对象**整体重新赋值**成新对象，为什么页面也不更新？
2. Vue 3 的响应式用 **Proxy** 实现、Vue 2 用 `Object.defineProperty`。**为什么 Vue 3 里数组下标赋值、对象新增属性不需要再写 `Vue.set` 了**？Proxy 还能做到哪些 Vue 2 做不到的事？
3. Vue 项目 `npm run build` 之后**首屏加载很慢**，你会从哪几个方向优化（路由懒加载、按需引入、分包、gzip、图片）？另外**开发环境用 devServer proxy 配过跨域，为什么上线后还会报跨域**？

<details>
<summary>标准参考答案</summary>
<p><strong>问题1①（解构丢失响应式）</strong>：<code>reactive(obj)</code> 返回的是一个 <strong>Proxy</strong>（可以理解为「给对象装了一个拦截器」），响应式是靠这个 Proxy 的 get / set 拦截实现的。<code>const { name } = state</code> 相当于<strong>把当时的值复制了一份出来</strong>，拿到的是一个<strong>普通字符串</strong>，跟原来那个 Proxy 再没关系，改它当然不触发更新。解法：用 <code>toRefs(state)</code> 或 <code>toRef(state, 'name')</code> 解构（这样拿到的是「和原对象保持连接的引用」），或干脆用 <code>ref</code> 存对象。</p>
<p><strong>问题1②（ref 为什么必须写 .value）</strong>：<strong>Proxy 只能代理对象，代理不了字符串、数字这类基础类型</strong>。所以 Vue 对基础类型的做法是用 <code>ref</code> 把它包成一个 <code>{ value: x }</code> 的对象，再对这个对象做代理——<strong>这就是 script 里必须写 <code>.value</code> 的根本原因</strong>。<code>reactive</code> 只用于对象 / 数组，读写属性不用 <code>.value</code>；<code>ref</code> 既能包基础类型也能包对象（内部会自动转成 reactive）。<strong>模板里 ref 会自动解包不用写 .value，script 里必须写</strong>，漏写是新手最常见的错。</p>
<p><strong>问题1③（整体重新赋值不生效）</strong>：<code>state = { ...state, age: 2 }</code> 是把变量 <code>state</code> 指向了一个<strong>全新的普通对象</strong>，而模板里绑定的还是原来那个 Proxy 的地址，所以视图不再更新。解法：<strong>用 <code>Object.assign(state, newVal)</code> 逐字段赋值</strong>，或改用 <code>ref</code> 存对象（<code>state.value = {...}</code> 是安全的，因为改的是 <code>value</code> 属性、会走 set 拦截）。<strong>后端类比</strong>：这就像你把一个被很多地方引用的对象换成了新对象，其他持有旧引用的地方感知不到。</p>
<p><strong>问题2（响应式原理：一句话）</strong>：<strong>数据变了，用到这个数据的地方自动重新执行</strong>。中间靠两步——读数据时把「谁在读我」记下来（track，依赖收集），写数据时通知它们重新执行（trigger，派发更新）。<strong>后端类比</strong>：类似 ORM / 缓存的「变更通知」机制，框架替你维护了一张「字段 → 用到它的渲染任务」的订阅表。<strong>Vue 2 的做法</strong>：用 <code>Object.defineProperty</code> <strong>逐个属性</strong>定义 getter / setter，getter 里收集依赖、setter 里派发更新。<strong>三个硬伤</strong>：① 只能劫持<strong>初始化时已经存在的属性</strong>，新增 / 删除检测不到 → 必须写 <code>Vue.set</code> / <code>this.$set</code>；② <strong>数组</strong>的下标赋值 <code>arr[0] = x</code> 和改 <code>arr.length</code> 检测不到 → 只能靠重写 push / pop / shift / unshift / splice / sort / reverse 七个方法兜底；③ 初始化时要<strong>递归遍历整个对象</strong>把所有属性都转换一遍，大对象首屏会慢。<strong>Vue 3 的做法</strong>：用 ES6 的 <strong>Proxy</strong> 拦截整个对象（能拦 get / set / deleteProperty / has / ownKeys 等十几种操作），读属性走 get 做 <code>track()</code>、写 / 删走 set / deleteProperty 做 <code>trigger()</code>，依赖存在一个 <strong>WeakMap → Map → Set</strong> 的三级结构里（即「对象 → 属性 → 用到它的 effect 集合」），配套用 <code>Reflect</code> 保证默认读写行为和 this 指向正确。<strong>四大好处</strong>：① 新增 / 删除属性、数组下标、length、Map / Set 全都拦得住，<strong>不用再写 $set</strong>；② <strong>懒代理</strong>——只有访问到某个嵌套对象时才把它转成响应式，初始化更快；③ 能原生支持 Map / Set / WeakMap / WeakSet；④ 拦截是「对象级」的，不依赖预先知道有哪些属性。</p>
<p><strong>问题3（打包优化）</strong>：<code>npm run build</code> 产出 <code>dist</code> 目录（纯静态文件：index.html + 带 hash 的 js / css / 图片），丢到 Nginx 静态目录或 OSS + CDN 即可。<strong>优化方向（能说出 4 个以上合格）</strong>：① <strong>路由懒加载</strong>——<code>component: () =&gt; import('@/views/User.vue')</code>，构建工具自动分包，首屏只加载需要的页面代码；② <strong>组件库按需引入</strong>——用 <code>unplugin-vue-components</code> + <code>unplugin-auto-import</code> 自动按需引入（Element Plus 全量引入包很大）；③ <strong>手动分包</strong>——<code>build.rollupOptions.output.manualChunks</code> 把 vue、element-plus 拆成独立 chunk，充分利用浏览器缓存；④ <strong>gzip / brotli</strong>——构建插件或 Nginx 开启，体积能压到三分之一；⑤ 图片压缩转 WebP、字体子集化、<strong>生产关闭 sourcemap</strong>；⑥ 大依赖走 CDN 外链 + externals；⑦ 首屏骨架屏。<strong>度量</strong>：用 Lighthouse 或 Chrome Performance 面板量化，关注 <strong>LCP</strong>（最大内容绘制，衡量首屏）、<strong>INP</strong>（交互响应）、<strong>CLS</strong>（累计布局偏移）。</p>
<p><strong>问题3（为什么上线后还会报跨域）</strong>：因为 <strong>proxy 只在开发环境生效</strong>——Vite / webpack 的 devServer 是你本地跑的一个 Node 服务，上线后它根本不存在，浏览器直接请求 <code>/api/xxx</code> 打到前端自己的服务器（Nginx）上，要么 404、要么被当成静态路径处理，于是又变成跨域。<strong>正确做法</strong>：生产由 Nginx 做反向代理 <code>location /api/ { proxy_pass http://后端地址; }</code>，或者由后端开 CORS。这是新人上线时最常踩的坑之一。</p>
<p><strong>常见坑合集（能讲出 3-4 个就是真用过 Vue 3）</strong>：① 响应式丢失（reactive 解构 / 整体重新赋值 / ref 漏写 .value）；② <strong>key 用数组下标</strong>——列表头部插入、删除或排序时下标平移，框架会误以为「下标相同的还是同一个节点」而错误复用，导致<strong>输入框内容错位、勾选状态错位</strong>，必须用后端返回的稳定业务 id（也不要用 <code>Math.random()</code>，每次渲染都变等于全部销毁重建）；③ <strong>v-if 与 v-for 写在同一元素上</strong>——<strong>Vue 3 中 v-if 优先级高于 v-for（Vue 2 恰好相反）</strong>，v-if 先执行会拿不到 v-for 的变量而报错，正确做法是用 <code>&lt;template v-for&gt;</code> 包一层，或<strong>更推荐用 computed 先把列表过滤好</strong>；④ 改完数据<strong>立刻读 DOM 是旧值</strong>——Vue 的 DOM 更新是<strong>异步批量</strong>的（放进微任务队列，等同一轮数据都改完再一次性渲染），要 <code>await nextTick()</code> 之后再操作（弹窗打开后让输入框聚焦、初始化 echarts 前拿容器尺寸都是这个场景）；⑤ <strong>内存泄漏</strong>——setInterval、addEventListener、echarts 实例、事件总线订阅，没在 <code>onUnmounted</code> 里清理；⑥ 路由参数变化（<code>/user/1</code> → <code>/user/2</code>）组件<strong>不会重建</strong>、<code>onMounted</code> 不再执行，要 <code>watch(() =&gt; route.params.id, fetchData)</code>；⑦ scoped 样式改不了子组件内部样式 → 用 <strong><code>:deep(.el-input__inner)</code></strong>（<strong>Vue 3 的写法，旧的 <code>::v-deep</code> / <code>/deep/</code> 已废弃</strong>）；⑧ <strong>Vue 3 已移除</strong> <code>$on</code> / <code>$off</code> / <code>$once</code> 事件总线、<code>$children</code>、<code>$listeners</code>（并入 <code>$attrs</code>）、<code>filter</code>、<code>v-on.native</code>。</p>
<p><strong>组件通信（JD 要求，简述即可）</strong>：父传子用 <strong>props</strong>（<code>defineProps</code>，可带类型和默认值）；子传父用 <strong>emit</strong>（<code>defineEmits</code>）；双向绑定用 <strong>v-model</strong>——Vue 3 组件上默认对应 prop 名 <code>modelValue</code> + 事件 <code>update:modelValue</code>，<strong>可以绑多个</strong>（<code>v-model:title</code>、<code>v-model:visible</code>）；父调子方法要子组件 <code>defineExpose({ reset, validate })</code>、父组件用 ref 调用（<strong>Vue 3 里 ref 拿到的实例默认不暴露内部东西，必须 defineExpose，这是和 Vue 2 的重要区别</strong>）；跨层用 <strong>provide / inject</strong>（建议 provide 时用 <code>readonly</code> 包一层）；全局用 <strong>Pinia</strong>（<strong>没有 mutations</strong>，只剩 state / getters / actions，actions 里可直接同步或异步改 state；<strong>解构 store 要用 <code>storeToRefs</code></strong>，否则丢响应式）。</p>
<p><strong>判断锚点</strong>：能讲清响应式丢失的三个坑并给出 toRefs / Object.assign 解法 → 真写过 Vue 3；能说清 Proxy 相比 defineProperty 的具体改进（不用 $set、懒代理、支持 Map/Set）→ 懂原理而不是背八股；能列出 4 个以上打包优化手段并知道 proxy 上线失效的原因 → 独立负责过上线；只会用但讲不出任何坑 → 初级。</p>

## 第 6 题　jQuery / DOM 操作、工程化与后台语言 / SQL

**问题**：
1. jQuery 的**链式调用是怎么实现的**（`$('div').css('color','red').addClass('a')` 为什么能一路点下去）？`$(document).ready` 和 `window.onload` 有什么区别？**现在的新项目还用 jQuery 吗、为什么**？
2. 要往页面里**一次性插入 1000 条列表数据**，怎么写性能才不卡？说下你常用的**原生 DOM API**。
3. JD 要求「了解一门后台开发语言和基本 SQL」：你熟悉哪一门（java / python / nodejs / go 等）？用它**实际做过什么**（起过 Node 服务 / 写过接口 / 写过数据处理脚本）？**LEFT JOIN 和 INNER JOIN 的区别**是什么？`GROUP BY` 之后要对聚合结果做过滤用什么关键字、它和 `WHERE` 有什么区别？

<details>
<summary>标准参考答案</summary>
<p><strong>问题1（jQuery 是什么、链式调用原理）</strong>：jQuery 是 2006 年诞生的库，核心价值是「<strong>封装 DOM 操作 + 抹平浏览器兼容差异</strong>」（那个年代 IE 和其他浏览器 API 差异巨大）。核心机制：<code>$(选择器)</code> 返回一个 <strong>jQuery 对象</strong>（类数组，包着一批 DOM 节点并提供一堆方法）。<strong>链式调用的原理：每个方法执行完都 <code>return this</code>（返回 jQuery 对象本身）</strong>，所以能 <code>.css().addClass().on()</code> 一路点下去。<strong>事件委托写法</strong>：<code>$('#list').on('click', '.del', fn)</code>——带第二个选择器的写法就是委托，等于把监听绑在父元素上，动态新增的行也有效。</p>
<p><strong>问题1（ready vs onload）</strong>：<code>$(document).ready</code>（对应原生 <code>DOMContentLoaded</code>）是 <strong>DOM 树构建完成</strong>就触发，<strong>不等图片、样式等资源加载完</strong>，可以绑多个、按注册顺序执行；<code>window.onload</code> 是<strong>所有资源都加载完</strong>才触发，且只能绑一个（后写的会覆盖前面的）。所以操作 DOM 一般用 ready，要等图片尺寸才算完就用 onload。</p>
<p><strong>问题1（现在还用不用、为什么）</strong>：新项目基本不用了，原因是<strong>理念冲突</strong>——Vue 这类框架是「<strong>数据驱动</strong>」：你只改数据，框架负责把 DOM 更新到和数据一致；jQuery 是「<strong>直接操作 DOM</strong>」。两者混用时，jQuery 改了 DOM 但框架不知道，<strong>框架下次渲染就会把它覆盖掉，导致视图和数据不一致</strong>——这是最难排查的一类 bug。再加上 jQuery 约 30KB（gzip 后）的体积对现代项目是负担，DOM API 和浏览器兼容性现在也都不是问题了。<strong>仍然保留的场景</strong>：老系统维护、内部后台（<strong>easyUI / layui 这类面向后台的 UI 库</strong>——特点是「配置式」，写一段 HTML + 一段 JS 配置就能出表格、表单、弹窗，适合内部后台快速交付，缺点是样式定制和移动端支持弱）、快速写活动页 / 小页面。</p>
<p><strong>问题2（一次性插 1000 条数据怎么写性能不差）</strong>：核心是<strong>减少重排次数</strong>。① 用 <strong>DocumentFragment</strong>（内存里的临时容器）：在 fragment 里循环创建 1000 个节点，最后<strong>只插入页面一次</strong>，把 1000 次重排降成 1 次；② 或用 <code>innerHTML</code> / <code>insertAdjacentHTML</code> 拼好字符串一次性写入（比循环 appendChild 快，<strong>注意别把用户输入直接拼进去，有 XSS 风险</strong>）；③ <strong>读写分离</strong>，别在循环里交替写样式又读 <code>offsetHeight</code>；④ 用 <code>classList</code> 改 class 而不是逐个改 style；⑤ <strong>更根本的方案：虚拟滚动</strong>——只渲染可视区域那十几条，1000 条数据只生成十几个 DOM；⑥ 事件用<strong>委托</strong>绑在父容器上，而不是绑 1000 个监听。</p>
<p><strong>问题2（常用原生 DOM API）</strong>：<code>document.querySelector / querySelectorAll / getElementById / createElement</code>；<code>el.classList.add / remove / toggle / contains</code>；<code>el.dataset</code>（读写 <code>data-*</code> 属性）；<code>appendChild / insertBefore / remove / replaceWith / cloneNode</code>；<code>setAttribute / getAttribute</code>；<strong><code>el.getBoundingClientRect()</code></strong>（拿元素位置和尺寸，做吸顶、滚动定位）；<strong>IntersectionObserver</strong>（图片懒加载、曝光埋点——比监听 scroll 性能好得多，由浏览器异步回调，不触发主线程布局计算）；<strong>ResizeObserver</strong>（监听元素尺寸变化，做图表自适应比 window.resize 更准）；<strong>MutationObserver</strong>（监听 DOM 变化）。</p>
<p><strong>工程化与上线流程（判断锚点，可作追问）</strong>：构建工具 <strong>Vite</strong>（新一代，开发时利用浏览器原生 ESM 按需编译、秒级启动；依赖用 esbuild 预构建；生产用 Rollup 打包）vs <strong>Webpack</strong>（先整体打包再启动，项目越大越慢；<strong>loader</strong> 翻译各种文件如 ts→js、scss→css，<strong>plugin</strong> 扩展构建流程）。<strong>工程化配套</strong>：包管理 npm / yarn / pnpm，<strong>lock 文件必须提交</strong>（保证团队和 CI 装到完全相同的版本，避免「我这能跑你那不行」）；Node 版本用 <code>.nvmrc</code> 固定；<strong>ESLint</strong>（查语法错误和潜在 bug）+ <strong>Prettier</strong>（统一格式）+ <strong>husky + lint-staged</strong> 在 commit 前自动跑 lint。<strong>上线流程</strong>：需求评审 → 技术方案 → 开发自测 → 代码评审 → 提测联调 → 回归 → 上线（灰度发布、保留可回滚版本）→ 监控（Sentry 上报 JS 报错率和接口失败率）。<strong>回滚</strong>：静态资源用带 hash 的文件名 + 保留历史版本目录，出问题把 Nginx 指向上一个版本目录，<strong>秒级回滚、不需要重新构建</strong>。<strong>判断锚点</strong>：能说出 Vite / webpack 的大致区别 → 用过现代工程化；能说出「上线后看监控指标、有问题按版本号快速回滚」→ 有完整交付经验；只会说「npm run build 然后扔服务器」→ 经验偏浅。</p>
<p><strong>问题3（后台语言了解程度）</strong>：JD 第 10 条只要求「<strong>了解</strong>」——不考后端框架源码，而是看前端能否<strong>看懂接口、写简单脚本或中间层、和后端聊得清</strong>。前端最常接触的是 <strong>Node.js</strong>：用 Express / Koa 起一个 BFF（Backend For Frontend，给前端专用的聚合接口层，把多个后端接口拼好再返回给页面），或写构建 / 数据处理脚本；也有人会 Python / Go / Java。<strong>判断锚点</strong>：能具体说出「用什么写过什么、解决了什么问题」→ 合格且加分；只能说「了解一点、没实际写过」→ 勉强符合 JD 最低要求；完全不会、也讲不出任何接口联调经历 → 不满足 JD 第 10 条。</p>
<p><strong>问题3（JOIN 区别）</strong>：<strong>INNER JOIN 只保留两边都匹配上的行</strong>——「查用户及其订单」会漏掉没下过单的用户；<strong>LEFT JOIN 以左表为主、左表全部保留</strong>，右表没匹配到的字段补 <strong>NULL</strong>——「所有用户都要列出来，没下过单的订单部分显示空」就用它。典型场景：统计「每个用户下过几单、没下过的显示 0」，必须用 LEFT JOIN 再对右表做聚合；「找出从没下过单的用户」用 <code>LEFT JOIN ... WHERE orders.id IS NULL</code>。<strong>判断锚点</strong>：能说清「INNER 只留两边都有，LEFT 左表全保留、没匹配补 NULL」→ 合格；能举出「查未下单用户」的具体写法 → 加分。</p>
<p><strong>问题3（GROUP BY + HAVING）</strong>：按用户分组统计订单数：<code>SELECT user_id, COUNT(*) AS cnt FROM orders GROUP BY user_id HAVING COUNT(*) &gt; 10</code>。<strong>关键区别</strong>：<strong>WHERE 在分组之前过滤原始行</strong>（如先只看金额大于 0 的订单），<strong>HAVING 在分组之后过滤聚合结果</strong>（如只保留下单超过 10 次的组）；<strong>聚合函数条件（COUNT / SUM / AVG 的结果）只能写在 HAVING 里</strong>，写在 WHERE 会报错。补充一个高频点：<strong>索引</strong>——类比「书的目录」，能加速 WHERE / JOIN / ORDER BY 查询，但会占存储、拖慢写入，只对高频查询字段加。<strong>判断锚点</strong>：能说清「分组后过滤用 HAVING、WHERE 是分组前」→ 合格；能把 COUNT + HAVING 组合写对 → 加分；知道索引的作用与代价 → 加分。</p>
