## 第 2 题　并发编程：线程池隔离与线上排障

**问题**：
1. 你们高并发场景里是怎么用线程池的？`ThreadPoolExecutor` 的**核心线程数（corePoolSize）、最大线程数（maximumPoolSize）、空闲线程存活时间（keepAliveTime 与时间单位）、任务队列（workQueue 的类型与容量）、线程工厂（threadFactory）、拒绝策略（handler）**这几个参数分别是多少、依据什么定的？
2. 线上出现过任务堆积或者被拒绝（RejectedExecutionException）吗？当时怎么**排查和处理**的？
3. 多线程里最容易踩的坑有哪些？比如 synchronized 的**锁升级**、**ThreadLocal 内存泄漏**，分别是什么原理、怎么避免？

**高频可追问（按实际情况选问）**：
- 任务提交到线程池之后，完整的处理流程是什么（核心线程 → 队列 → 最大线程 → 拒绝）？
- 为什么不建议用 `Executors` 的工厂方法创建线程池（FixedThreadPool / CachedThreadPool 各自的隐患）？
- RejectedExecutionException 怎么排查与预防（队列水位监控 / 线程 dump / 参数怎么定）？
- synchronized 的锁升级过程（无锁 → 偏向锁 → 轻量级锁 → 重量级锁）？每一级到底做了什么、为什么这么设计？
- ThreadLocal 为什么会导致内存泄漏（Entry 的 key 是弱引用、value 是强引用，用完必须 remove）？
- 有哪几种拒绝策略（AbortPolicy / CallerRunsPolicy / DiscardPolicy / DiscardOldestPolicy），各自适用什么场景？

<details>
<summary>标准参考答案</summary>
<p><strong>问题1（线程池参数①：corePoolSize / maximumPoolSize / keepAliveTime）</strong>：线程池的作用是用一组可控的线程反复执行大量短任务，避免每个任务都新建线程把资源耗尽。<strong>corePoolSize 核心线程数</strong>——长期保活的线程数量，空闲也不回收（除非开了 allowCoreThreadTimeOut）；怎么定：<strong>CPU 密集型</strong>（纯计算、几乎不等）≈ CPU 核数 或 核数+1，<strong>IO 密集型</strong>（要等数据库 / Redis / 远程接口返回）可以放大到 <strong>2×核数</strong>甚至更高，更精确的估法是「核数 ×（1 + 等待时间 / 计算时间）」。<strong>maximumPoolSize 最大线程数</strong>——队列排满后允许临时扩容到的上限；注意<strong>只有「有界队列 且 已排满」时才会创建超过核心数的线程</strong>。<strong>keepAliveTime + unit 空闲存活时间</strong>——超出核心数的那些「临时线程」，空闲多久后被回收掉，缩回核心线程数。</p>
<p><strong>问题1（线程池参数②：workQueue / threadFactory / handler）</strong>：<strong>workQueue 任务队列</strong>——核心线程都忙时，新任务排队的地方；推荐 <strong>ArrayBlockingQueue（有界，必须指定容量）</strong>；<strong>LinkedBlockingQueue 不指定容量时默认 Integer.MAX_VALUE，相当于无界，任务一堆积就把内存撑爆 OOM</strong>；SynchronousQueue 不存储任务、直接移交给线程（要配合较大的 maximumPoolSize）；PriorityBlockingQueue 按优先级出队。<strong>threadFactory 线程工厂</strong>——给线程起名字、设优先级、设是否守护线程；<strong>自定义有意义的名字是线上排障的关键</strong>：jstack 里能看到「order-pool-1」而不是毫无信息量的「pool-1-thread-1」。<strong>handler 拒绝策略</strong>——队列满且线程数已达上限时的兜底动作，四种策略见下方追问；选型只看一件事：<strong>这个任务能不能丢</strong>——下单、支付这类核心业务不能丢，用 CallerRunsPolicy 做背压或落库重试；埋点、日志上报这类可丢的才用 DiscardPolicy。</p>
<p><strong>问题2（任务堆积 / RejectedExecutionException 排查处理）</strong>：RejectedExecutionException 说明队列已满且线程数已达 maximumPoolSize。排查三步：① 看监控——队列剩余容量、activeCount（活跃线程数）、completedTaskCount，判断到底是「真的消费不过来」还是「某个任务卡死不返回」；② 用 jstack 抓线程栈，看线程卡在哪（锁竞争 / 慢 SQL / 外部接口超时 / 死循环）；③ 核对拒绝策略与有没有补偿兜底。处理：扩容消费者或调大队列 / 最大线程数、优化慢任务（异步化、加缓存、限流上游）；核心任务改用 CallerRunsPolicy 做背压，或先把任务落库再异步重试，<strong>绝不能静默丢弃</strong>。</p>
<p><strong>问题3①（synchronized 锁升级 概览）</strong>：JVM 会按<strong>竞争激烈程度</strong>把锁从轻到重分四级——<strong>无锁 → 偏向锁 → 轻量级锁 → 重量级锁</strong>，逐级升级，能用轻的就不用重的。一句话理解每一级：<strong>偏向锁</strong>＝记住线程 ID，一个人用时几乎不要钱；<strong>轻量级锁</strong>＝CAS + 自旋，人少时不用惊动操作系统；<strong>重量级锁</strong>＝找操作系统排队挂起，人多了才值这个价。逐级详解见下方追问。</p>
<p><strong>问题3②（ThreadLocal 内存泄漏）</strong>：ThreadLocal 相当于「每个线程各自带一份的变量副本」（常用来在一次请求链路里透传用户信息）。每个线程内部有一个 ThreadLocalMap，里面每个 Entry 的 <strong>key 是弱引用</strong>（指向 ThreadLocal 对象）、<strong>value 是强引用</strong>（指向你存进去的值）。当 ThreadLocal 对象本身被回收后，key 变成 null，但 <strong>value 还被强引用着，不会被 GC</strong>；而<strong>线程池里的线程是长期存活的</strong>（不会随任务结束而销毁），于是这些 value 一直挂在线程上越积越多 → 内存泄漏，还会造成<strong>脏数据</strong>（下一个任务复用到同一个线程时，读到了上一个用户的数据）。<strong>规范用法：用完后在 try-finally 里 remove()。</strong></p>
<p><strong>追问：任务提交后的完整处理流程</strong>：提交任务（execute / submit）后按这个顺序判断：① 当前线程数 &lt; corePoolSize → <strong>直接新建核心线程</strong>执行；② 线程数已达核心线程数 → 任务<strong>进队列排队</strong>；③ <strong>队列已满</strong> 且 线程数 &lt; maximumPoolSize → <strong>新建临时线程</strong>执行（注意执行的是<strong>刚提交的这个新任务</strong>，不是队列里排最久的那个）；④ <strong>队列已满</strong> 且 线程数已达 maximumPoolSize → 触发<strong>拒绝策略</strong>。临时线程空闲超过 keepAliveTime 后被回收，缩回核心线程数。<strong>关键认知：只有队列是有界的且已排满，才会创建超过核心线程数的线程</strong>——所以一旦用了无界队列（LinkedBlockingQueue 不设容量），maximumPoolSize 和拒绝策略就永远不生效，只会一路堆积到 OOM。</p>
<p><strong>追问：为什么不建议使用 Executors 工厂方法</strong>：Executors 的工厂方法都藏着「无界」风险：① <strong>newFixedThreadPool / newSingleThreadExecutor</strong> 用的是<strong>无界</strong> LinkedBlockingQueue（默认容量 Integer.MAX_VALUE），任务堆积时根本不触发拒绝策略，直接把堆内存撑爆 OOM；② <strong>newCachedThreadPool</strong> 的 maximumPoolSize 是 Integer.MAX_VALUE，高并发下会无限创建线程 → OOM 或系统假死；③ <strong>newScheduledThreadPool</strong> 用的是无界延迟队列，而且任务里抛出未捕获异常会导致该定时任务<strong>静默停止</strong>。<strong>生产必须手动 <code>new ThreadPoolExecutor(...)</code></strong>，显式指定有界队列容量、拒绝策略和带名字的线程工厂（阿里 Java 开发手册强制要求）。</p>
<p><strong>追问：RejectedExecutionException 怎么排查与预防</strong>：排查同上（先看队列水位与 activeCount，再用 jstack 定位线程阻塞点）。<strong>预防</strong>更关键：① 给队列水位、活跃线程数、拒绝次数<strong>加监控告警</strong>，别等用户报障才发现；② 线程池参数<strong>靠压测定</strong>，不能拍脑袋；③ 按业务<strong>隔离线程池</strong>，别让慢业务（如导出、对账）把快业务（如下单）的线程全占住；④ 核心任务即使被拒绝也要有<strong>落库 + 重试</strong>的兜底通道。</p>
<p><strong>追问：synchronized 锁升级（背景：为什么要有锁升级）</strong>：早期 synchronized 很「重」——一上来就向<strong>操作系统</strong>申请互斥锁，抢不到锁的线程要被<strong>挂起</strong>（从用户态切到内核态）。一次这种切换的代价比执行几条普通指令慢几千倍，非常昂贵。但实际很多代码段<strong>大部分时间只有一个线程在进</strong>，根本没竞争，白白付这个代价不划算。所以 JDK 1.6 起引入锁升级：按竞争激烈程度<strong>逐级加重</strong>，能省则省——这就是锁升级要解决的核心问题。</p>
<p><strong>追问：synchronized 锁升级（无锁 → 偏向锁）</strong>：<strong>无锁</strong>：对象刚创建、还没任何线程来加锁。<strong>偏向锁</strong>——应对「一段时间内只有同一个线程反复进出这段代码」：JVM 把<strong>当前线程 ID 直接记在对象头里</strong>（对象头＝每个 Java 对象自带的一小块元数据区，存 GC 年龄、锁状态、哈希码等信息）。这个线程之后再进来，<strong>只要看一眼对象头里的 ID 是自己，就直接进入，连一次 CAS 都不用做</strong>，几乎零开销。一旦出现<strong>第二个线程</strong>来竞争，偏向锁就被<strong>撤销</strong>并升级为轻量级锁（撤销需要等到安全点，本身有成本）。</p>
<p><strong>追问：synchronized 锁升级（轻量级锁）</strong>：应对「线程交替执行、竞争很少、基本不阻塞」：线程先在自己的<strong>栈帧</strong>里开辟一块叫 Lock Record 的空间，把对象头里的 Mark Word 拷贝进去，然后用 <strong>CAS</strong>（Compare And Swap，比较并交换——<strong>一条 CPU 原子指令</strong>：只有发现值没被别人改过时才写入）尝试把对象头指向自己的 Lock Record；<strong>CAS 成功＝拿到锁</strong>，失败说明有竞争，线程就<strong>自旋</strong>（不挂起，而是空转循环重试一小会儿）。「轻」在哪：<strong>线程不挂起、不切换到内核态</strong>，省掉了上下文切换的大开销。缺点：<strong>自旋是空转烧 CPU</strong>，如果锁里面执行的是慢 SQL 这类长任务，自旋的线程会白白吃掉 CPU，反而更糟。JDK 1.6 之后自旋次数是<strong>自适应</strong>的（JVM 根据这把锁以往自旋的成功率动态调整），不再是固定次数。</p>
<p><strong>追问：synchronized 锁升级（重量级锁）</strong>：应对「竞争激烈、自旋也抢不到」：自旋超过阈值、或自旋线程数过多，就升级为重量级锁——向<strong>操作系统</strong>申请互斥量（mutex / monitor），抢不到锁的线程<strong>直接挂起、进入阻塞队列</strong>，等锁释放时再由操作系统唤醒。代价：<strong>用户态 ↔ 内核态切换 + 线程上下文切换</strong>，很慢；好处：<strong>阻塞的线程不占用 CPU</strong>，所以反而适合「锁持有时间长、竞争激烈」的场景（这正是自旋应付不了的场景）。这就解释了实际中「加锁后反而变慢」的现象——竞争一激烈，锁就升到重量级，每次加解锁都要走操作系统。</p>
<p><strong>追问：synchronized 锁升级（总结与加分点）</strong>：<strong>总结一句</strong>：偏向＝记住线程 ID（一人用几乎免费）；轻量＝CAS + 自旋（人少不惊动操作系统）；重量＝操作系统排队挂起（人多才值）。<strong>升级方向是 无锁 → 偏向 → 轻量 → 重量，在加锁竞争过程中是单向的</strong>（不会从重量级退回轻量级继续竞争）；<strong>锁释放后</strong>对象会回到无锁状态，下次加锁再重新从低级走起。<strong>加分点</strong>：① <strong>JDK 15 起偏向锁已默认关闭并被废弃</strong>（现代程序普遍有竞争，维护偏向 / 撤销的开销大于收益，JEP 374）；② JIT 还会做<strong>锁消除</strong>（编译期发现这个对象不可能被其他线程共享，直接把锁去掉，如方法内的局部 StringBuffer）和<strong>锁粗化</strong>（把相邻的多次加解锁合并成一次）。</p>
<p><strong>追问：ThreadLocal 为什么内存泄漏</strong>：ThreadLocalMap 的 Entry 中 <strong>key 是弱引用</strong>（指向 ThreadLocal 对象）、<strong>value 是强引用</strong>（指向你存的值）。ThreadLocal 对象被回收后 key 变 null，但 value 仍被强引用着；线程池里的线程长期存活不会销毁，value 就一直挂在线程上 → 既<strong>内存泄漏</strong>又产生<strong>跨任务脏数据</strong>。因此必须 <strong>try-finally 中 remove()</strong>。补充：想让子线程读到父线程的值要用 <code>InheritableThreadLocal</code>，但它在<strong>线程池场景失效</strong>（线程是复用的，只在创建时拷贝一次），线程池里透传上下文建议用 TransmittableThreadLocal 或显式传参。</p>
<p><strong>追问：四种拒绝策略与适用场景</strong>：<strong>AbortPolicy</strong>（默认，直接抛 RejectedExecutionException，让调用方立刻感知失败，适合不允许静默丢失的场景）；<strong>CallerRunsPolicy</strong>（让<strong>提交任务的那个线程自己执行</strong>，相当于给上游施加背压、自然削峰，而且<strong>不丢任务</strong>，是核心业务最常用的选择）；<strong>DiscardPolicy</strong>（<strong>静默丢弃</strong>，不抛任何异常，生产慎用）；<strong>DiscardOldestPolicy</strong>（丢弃队列里<strong>排最久</strong>的那个任务，然后重试提交当前任务）。选型只问一句：<strong>这任务能不能丢</strong>——核心链路优先 CallerRunsPolicy 或自定义策略（落库 + 告警 + 重试），可丢弃的埋点 / 统计才用 Discard。</p>
<p><strong>常见坑</strong>：用无界队列导致 maximumPoolSize 与拒绝策略形同虚设；不同业务共用一个线程池，慢业务（导出、对账）把快业务（下单）的线程占满拖垮——应按业务<strong>隔离线程池</strong>；参数拍脑袋不压测；ThreadLocal 用完不 remove；Atomic 类的 <strong>ABA 问题</strong>（用 AtomicStampedReference 加版本号解决）、<strong>volatile 不保证复合操作原子性</strong>（i++ 仍需加锁或用原子类）、<strong>死锁</strong>（按固定顺序加锁 / 用 tryLock 加超时）。</p>
</details>

## 第 3 题　MySQL 调优：慢 SQL 排查与索引失效

**问题**：
1. 一条 SQL 突然变慢，你怎么**排查定位问题、怎么优化**？
2. 哪些**具体的写法或者场景会导致索引失效**（用不上索引）？
3. 如果是大表（千万级），除了加索引还有哪些**具体的优化手段**（分库分表 / 读写分离 / 冷热分离）？

**高频可追问（按实际情况选问）**：
- 定位手段有哪些（慢查询日志、EXPLAIN 看 type/key/rows/Extra、SkyWalking / Arthas 定位慢调用）？
- 索引失效写法（like 前缀 %、对索引列做函数包裹、OR 连接非索引列、!= 、隐式类型转换、不满足最左前缀）？
- 优化手段（覆盖索引、联合索引字段顺序、深分页用延迟关联 / 游标）？
- 大表方案（读写分离、按什么分片键分库分表、冷热分离）？

<details>
<summary>标准参考答案</summary>
<p><strong>问题1（慢 SQL 排查定位 + 优化）</strong>：先开慢查询日志（slow_query_log）抓慢 SQL，再用 EXPLAIN 看执行计划——重点看 type（最好到 range/ref/const，最差 ALL 全表扫）、key（实际用到的索引）、rows（扫描行数）、Extra（Using filesort / Using temporary 是坏信号）；应用侧可用 SkyWalking / Arthas 定位是哪个接口慢。定位后：该建索引就建、能用覆盖索引（查询列都在索引里不用回表）最优、改写深分页、优化 join。</p>
<p><strong>问题2（索引失效写法 / 场景）</strong>：对索引列用函数（WHERE DATE(create_time)=...）、隐式类型转换（字符串列传数字）、like '%xx' 前模糊、OR 连接了非索引列、!= / &lt;&gt;、NOT IN、不满足联合索引最左前缀（如建了 (a,b,c) 却只查 b）——这些都会让优化器放弃索引走全表。</p>
<p><strong>问题3（大表优化：分库分表 / 读写分离 / 冷热分离）</strong>：读写分离（主写从读，分担读压）；分库分表（按用户 id / 订单号 hash 或按时间 range 分片，选好分片键避免跨片查询）；冷热分离（历史数据归档）；分析类查询必要时用 ClickHouse 等列存。</p>
<p><strong>追问：定位手段</strong>：慢查询日志 + EXPLAIN（type/key/rows/Extra）+ 应用监控 SkyWalking / Arthas 定位慢调用。</p>
<p><strong>追问：优化手段细节</strong>：覆盖索引避免回表；联合索引字段顺序高频等值在前、范围在后；深分页 LIMIT 100000,20 改写成「延迟关联」（先查主键再 join）或用游标 / 上一页最大 id 翻页；大结果集分批。</p>
<p><strong>追问：大表分片键选择</strong>：按访问最频繁、能均匀分布且不跨片查询的字段（如用户 id hash、订单号）分片，避免按易倾斜字段分片导致热点。</p>
<p><strong>常见坑</strong>：索引不是越多越好（拖慢写、占空间）；联合索引顺序要贴合查询；EXPLAIN 的 rows 是估值，真慢还要结合实际数据分布判断。</p>

## 第 4 题　Redis：缓存异常与分布式锁

**问题**：
1. 缓存穿透、击穿、雪崩分别是什么？你们线上**具体怎么预防**的？
2. 用 Redis 做**分布式锁**要注意什么（防死锁、误删、续期）？
3. 缓存和数据库的一致性怎么保证（先删缓存还是先更新库、延迟双删）？还有**热 key / 大 key** 你们怎么处理？

**高频可追问（按实际情况选问）**：
- 各异常预防手段（穿透：空值缓存 / 布隆过滤器；击穿：互斥锁 / 逻辑过期；雪崩：随机过期 + 多级缓存 + 高可用）？
- 分布式锁（SETNX + 过期、Redisson WatchDog 自动续期、释放前校验持有者、Redlock 争议）？
- 一致性（先更新库再删缓存、延迟双删、Canal 订阅 binlog 重试、失败补偿）？
- 热 key（本地缓存 + 打散）、大 key（拆分 / 分批删除）？

<details>
<summary>标准参考答案</summary>
<p><strong>问题1（穿透 / 击穿 / 雪崩 是什么 + 怎么预防）</strong>：① 穿透=查不存在的数据（缓存和库都没有），预防是缓存空值（短时间 TTL）或布隆过滤器拦截。② 击穿=某热点 key 过期瞬间大量请求打到库，预防是互斥锁重建缓存或逻辑过期（异步刷新）。③ 雪崩=大量 key 同时过期或 Redis 宕机，预防是给过期时间加随机值、用多级缓存、Redis 高可用（哨兵 / 集群）。</p>
<p><strong>问题2（分布式锁注意点）</strong>：用 SET key value NX PX 30000 原子加锁（value 用唯一标识如 UUID，释放前用 Lua 校验是自己持有的再删，防误删别人的锁）；风险是锁超时但业务没跑完——用 Redisson 的 WatchDog 默认每 10s 自动续期（默认锁 30s）；多节点可用 Redlock（但有争议，多数场景 Redisson 单集群足够）。</p>
<p><strong>问题3（缓存与库一致性 + 热 key / 大 key）</strong>：一致性推荐「先更新数据库，再删除缓存」（Cache-Aside），读时回填；删除失败用延迟双删（更新前删一次、更新后延迟再删）或 Canal 监听 binlog 异步删；强一致才上分布式事务，多数业务接受最终一致 + 重试补偿。热 key：本地缓存（Caffeine）+ Redis，或把热 key 打散到多个副本 key。大 key：拆分（按字段 / 分片）、删除用 UNLINK 异步避免阻塞。</p>
<p><strong>追问：各异常预防手段</strong>：穿透→空值缓存 / 布隆过滤器；击穿→互斥锁 / 逻辑过期；雪崩→随机过期 + 多级缓存 + 高可用。</p>
<p><strong>追问：分布式锁细节</strong>：SETNX+过期防死锁、Redisson WatchDog 续期、Lua 校验持有者防误删、Redlock 多节点（争议）。</p>
<p><strong>追问：一致性方案</strong>：先更库再删缓存、延迟双删、Canal 订阅 binlog 重试、失败补偿。</p>
<p><strong>常见坑</strong>：缓存与库双写不一致（先更库再删缓存 + 重试）；大 key 阻塞主线程；锁忘设过期导致死锁；用 DEL 而非 Lua 校验删除会误删。</p>
</details>

## 第 5 题　消息队列：可靠投递、幂等与积压治理

**问题**：
1. 用 MQ 做异步解耦时，怎么保证消息**不丢、也不重复消费（幂等）**？
2. 消息**积压**了（消费者跟不上）你们怎么**具体处理**的？
3. 延迟消息、顺序消息、死信队列分别用在什么**具体场景**、怎么实现？

**高频可追问（按实际情况选问）**：
- 不丢（生产者 confirm / 事务、Broker 持久化、消费者手动 ack）？
- 幂等（数据库唯一约束 / 去重表 / Redis 防重 key / 业务状态流转）？
- 积压（扩容消费者、批量消费、临时 topic 中转、死信兜底）？
- 延迟消息（订单关单）、顺序消息（同一分片）、死信（消费失败转移）？

<details>
<summary>标准参考答案</summary>
<p><strong>问题1（不丢 + 幂等）</strong>：不丢三环节——生产者开 confirm（RabbitMQ 发布确认 / Kafka acks=all）并监听失败重发；Broker 队列 / 主题开启持久化、多副本；消费者用手动 ack，处理成功再确认、失败不 ack 让重投。幂等——同一条消息因重试会重复消费，必须幂等：数据库唯一约束 / 去重表（消息 id 唯一）、Redis 防重 key（处理前 SETNX 消息 id）、或业务状态流转（已处理则跳过）；订单类用「订单号 + 状态」最稳妥。</p>
<p><strong>问题2（消息积压处理）</strong>：先扩容消费者实例 / 增加消费线程，提升单实例消费速度（批量拉取、批量落库）；短时消费不完，建临时 topic 把消息转移到更多分区多消费者并行消化，消费完再切回；长期积压要查是否有慢消费（如同步调外部接口超时），优化后再追平。</p>
<p><strong>问题3（延迟 / 顺序 / 死信消息）</strong>：延迟消息——RabbitMQ 用死信 + TTL 或延时插件，RocketMQ / Kafka 有原生延迟等级，典型「订单 30 分钟未支付自动关单」；顺序消息——同一业务 key 路由到同一分片 / 队列保证有序（如订单状态流转）；死信队列——消费多次失败的消息转入死信，人工排查不阻塞主流程。</p>
<p><strong>追问：不丢细节</strong>：生产者 confirm / 事务、Broker 持久化、消费者手动 ack 三者缺一不可。</p>
<p><strong>追问：幂等细节</strong>：唯一约束 / 去重表 / Redis 防重 key / 状态流转，订单用「订单号 + 状态」。</p>
<p><strong>追问：积压细节</strong>：扩容消费者、批量消费、临时 topic 中转、死信兜底。</p>
<p><strong>常见坑</strong>：自动 ack 导致丢消息；幂等没做导致重复下单 / 扣款；消费者里做同步远程调用拖慢队列；消息体过大撑爆 Broker。</p>
</details>

<details>
<summary>标准参考答案</summary>
<p><strong>问题1（注册发现 + 配置动态生效，以 Nacos 为例）</strong>：服务启动时把自身 ip:port 注册到 Nacos，消费者从 Nacos 拉取服务列表做负载均衡调用；实例宕机 Nacos 健康检查剔除，新实例上线自动被发现。配置中心把开关 / 阈值放 Nacos，应用监听配置变更事件，@RefreshScope 或监听回调动态生效，不用重启。</p>
<p><strong>问题2（统一入口 Gateway）</strong>：所有外部请求先过 Spring Cloud Gateway，在过滤器里做鉴权（校验令牌）、路由转发（按 path / 服务名）、限流（令牌桶 / 计数器）；与业务解耦，业务服务只管业务逻辑，安全与流控在边界统一收口。</p>
<p><strong>问题3（限流 / 熔断 / 降级，以 Sentinel 为例）</strong>：限流按 QPS / 线程数设阈值挡住突发流量；熔断用三种状态切换——Closed 正常，错误率超阈值切 Open 直接拒绝并走 fallback 降级，过冷却期进 Half-Open 放少量请求探测，成功则回 Closed 失败续 Open；降级 fallback 返回兜底数据保证主流程可用。</p>
<p><strong>问题4（分布式事务 + 链路追踪 / 灰度）</strong>：强一致用 Seata AT（自动生成回滚日志补偿）或 TCC（Try-Confirm-Cancel 三阶段，性能好但侵入大）；最终一致常用「本地消息表 / RocketMQ 事务消息」——本地事务和消息表同库写、后台任务投递、消费者幂等处理；选哪种看一致性要求与性能权衡。链路追踪用 SkyWalking / Sleuth + Zipkin，靠 traceId 串起跨服务调用；灰度发布按版本号 / 标签路由，先放少量流量验证再全量。</p>
<p><strong>追问：Nacos / Gateway / Sentinel</strong>：Nacos 注册发现 + 配置动态生效 + 健康检查剔除；Gateway 统一鉴权 / 路由 / 限流与业务解耦；Sentinel 阈值设定 + 熔断三状态 + fallback 降级。</p>
<p><strong>追问：分布式事务选型</strong>：Seata AT 自动补偿 / TCC 三阶段 / 消息最终一致性 / 本地消息表，按一致性要求与性能权衡。</p>
<p><strong>常见坑</strong>：注册中心网络分区误剔除（健康探针 + 多副本）；Gateway 限流阈值拍脑袋不设、大促被打爆；分布式事务滥用 Seata 致性能差，能用消息最终一致就别上强一致；熔断阈值只看错误率忽略慢调用。</p>
</details>
