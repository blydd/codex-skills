## 第 2 题　并发编程：线程池隔离与线上排障

**题目来源：岗位 JD**（多线程 / 并发，固定题；场景为通用高并发工程场景，不引用候选人旧项目；全部题目不得涉及 AI / 大模型相关内容）

**问题**：
1. 你们高并发场景里是怎么用线程池的？**核心线程数、队列类型与容量、拒绝策略**是怎么定的？
2. 线上出现过任务堆积或者被拒绝（RejectedExecutionException）吗？当时怎么**排查和处理**的？
3. 多线程里还有哪些容易踩的坑（如锁升级、ThreadLocal 内存泄漏）你在项目里实际遇到过？

**高频可追问（按实际情况选问）**：
- RejectedExecutionException 怎么排查（线程 dump / 队列水位监控 / 拒绝策略选择）？
- synchronized 的锁升级过程（无锁 → 偏向锁 → 轻量级锁 → 重量级锁）？
- ThreadLocal 为什么会导致内存泄漏（Entry 的 key 是弱引用、value 是强引用，用完必须 remove）？
- 有哪几种拒绝策略（AbortPolicy / CallerRunsPolicy / DiscardPolicy / DiscardOldestPolicy），各自适用什么场景？

<details>
<summary>标准参考答案</summary>
<p>线程池参数定性：核心线程数 corePoolSize 看业务是 CPU 密集（≈核数 +1）还是 IO 密集（可放大，如 2×核数或更高）；队列用有界队列（ArrayBlockingQueue / LinkedBlockingQueue 指定容量）防止 OOM；拒绝策略按业务容忍度选——不允许丢任务用 CallerRunsPolicy（调用方线程执行，可背压），允许丢用 DiscardPolicy，默认可抛异常 AbortPolicy。</p>
<p>任务堆积排查：先看监控 / 队列剩余容量与 activeCount，再用 jstack 抓线程栈看线程卡在哪（锁竞争 / 慢 IO / 死循环）；定位后扩容消费者、调大队列或优化慢任务（异步化、加缓存、限流上游）。</p>
<p>拒绝处理：RejectedExecutionException 说明队列满且达最大线程数；处理是扩容 + 限流 + 改用 CallerRunsPolicy 做背压，或把任务落库后异步重试，不能静默丢弃核心任务。</p>
<p>锁升级：synchronized 在 JVM 里从无锁经偏向锁（单线程）、轻量级锁（CAS 自旋）、重量级锁（操作系统互斥，线程阻塞）逐步升级，竞争越激烈开销越大；理解它才能解释「为什么加锁后反而慢」。</p>
<p>ThreadLocal 泄漏：ThreadLocalMap 的 key 是弱引用，value 是强引用，线程池线程长期存活且不 remove，value 不会被 GC，导致内存泄漏；规范用法是 try-finally 里 remove。</p>
<p>其他常见坑：Atomic 类的 ABA 问题（用 AtomicStampedReference）、volatile 不保证原子性（i++ 仍需锁或原子类）、死锁（按顺序加锁 / 用 tryLock 超时）。</p>
</details>

## 第 3 题　MySQL 调优：慢 SQL 排查与索引失效

**题目来源：岗位 JD**（MySQL 优化 / 索引失效 / 分库分表，固定题；通用工程场景，不引用候选人旧项目；全部题目不得涉及 AI / 大模型相关内容）

**问题**：
1. 一条 SQL 突然变慢，你怎么**排查定位问题、怎么优化**？
2. 哪些**写法或者场景会导致索引失效**（用不上索引）？
3. 如果是大表（千万级），除了加索引还有哪些优化手段（分库分表 / 读写分离）？

**高频可追问（按实际情况选问）**：
- 定位手段有哪些（慢查询日志、EXPLAIN 看 type/key/rows/Extra、SkyWalking / Arthas 定位慢调用）？
- 索引失效写法（like 前缀 %、对索引列做函数包裹、OR 连接非索引列、!= 、隐式类型转换、不满足最左前缀）？
- 优化手段（覆盖索引、联合索引字段顺序、深分页用延迟关联 / 游标）？
- 大表方案（读写分离、按什么分片键分库分表、冷热分离）？

<details>
<summary>标准参考答案</summary>
<p>排查定位：先开慢查询日志（slow_query_log）抓慢 SQL，再用 EXPLAIN 看执行计划——重点看 type（最好到 range/ref/const，最差 ALL 全表扫）、key（实际用到的索引）、rows（扫描行数）、Extra（Using filesort / Using temporary 是坏信号）；应用侧可用 SkyWalking / Arthas 定位是哪个接口慢。</p>
<p>优化方向：能走索引就建合适索引，能用覆盖索引（查询列都在索引里，不用回表）最优；深分页 LIMIT 100000,20 改写成「延迟关联」（先查主键再 join）或用游标 / 上一页最大 id 翻页；大结果集考虑分批。</p>
<p>索引失效典型写法：对索引列用函数（WHERE DATE(create_time)=...）、隐式类型转换（字符串列传数字）、like '%xx' 前模糊、OR 连接了非索引列、!= / &lt;&gt;、NOT IN、不满足联合索引最左前缀（如建了 (a,b,c) 却只查 b）——这些都会让优化器放弃索引走全表。</p>
<p>大表手段：读写分离（主写从读，分担读压）；分库分表（按用户 id / 订单号 hash 或按时间 range 分片，选好分片键避免跨片查询）；冷热分离（历史数据归档）；必要时用 ClickHouse 等列存做分析。</p>
<p>常见坑：索引不是越多越好（拖慢写、占空间）；联合索引顺序要贴合查询（高频等值在前、范围在后）；EXPLAIN 的 rows 是估值，真慢还要结合实际数据分布判断。</p>
</details>

## 第 4 题　Redis：缓存异常与分布式锁

**题目来源：岗位 JD**（Redis，固定题；通用工程场景，不引用候选人旧项目；全部题目不得涉及 AI / 大模型相关内容）

**问题**：
1. 缓存穿透、击穿、雪崩分别是什么？你们线上怎么**预防**的？
2. 用 Redis 做**分布式锁**要注意什么（防死锁、误删、续期）？
3. 缓存和数据库的一致性怎么保证（先删缓存还是先更新库、延迟双删）？还有**热 key / 大 key** 你们怎么处理？

**高频可追问（按实际情况选问）**：
- 各异常预防手段（穿透：空值缓存 / 布隆过滤器；击穿：互斥锁 / 逻辑过期；雪崩：随机过期 + 多级缓存 + 高可用）？
- 分布式锁（SETNX + 过期、Redisson WatchDog 自动续期、释放前校验持有者、Redlock 争议）？
- 一致性（先更新库再删缓存、延迟双删、Canal 订阅 binlog 重试、失败补偿）？
- 热 key（本地缓存 + 打散）、大 key（拆分 / 分批删除）？

<details>
<summary>标准参考答案</summary>
<p>三大异常：穿透=查不存在的数据（缓存和库都没有），解决是缓存空值（短时间 TTL）或布隆过滤器拦截；击穿=某个热点 key 过期瞬间大量请求打到库，解决是互斥锁重建缓存或逻辑过期（异步刷新）；雪崩=大量 key 同时过期或 Redis 宕机，解决是给过期时间加随机值、用多级缓存、Redis 高可用（哨兵 / 集群）。</p>
<p>分布式锁：用 SET key value NX PX 30000 原子加锁（value 用唯一标识如 UUID，释放前用 Lua 校验是自己持有的再删，防误删别人的锁）；风险是锁超时但业务没跑完——用 Redisson 的 WatchDog 默认每 10s 自动续期（默认锁 30s）；多节点可用 Redlock（但有争议，多数场景 Redisson 单集群足够）。</p>
<p>缓存一致性：推荐「先更新数据库，再删除缓存」（Cache-Aside），读时回填；删除失败可用延迟双删（更新前删一次、更新后延迟再删）或 Canal 监听 binlog 异步删；强一致场景才上分布式事务，多数业务接受最终一致 + 重试补偿。</p>
<p>热 key：某 key 访问极高，单节点扛不住——本地缓存（Caffeine）+ Redis，或把热 key 打散到多个副本 key；大 key：单个 value 过大（如大 list / hash）导致阻塞——拆分（按字段 / 分片）、大 key 删除用 UNLINK 异步删避免阻塞。</p>
<p>常见坑：缓存与库双写不一致（解决是先更库再删缓存 + 重试）；Redis 大 key 阻塞主线程；锁忘记设过期导致死锁；用 DEL 而非 Lua 校验删除会误删。</p>
</details>

## 第 5 题　消息队列：可靠投递、幂等与积压治理

**题目来源：岗位 JD**（MQ，固定题；通用工程场景，不引用候选人旧项目；全部题目不得涉及 AI / 大模型相关内容）

**问题**：
1. 用 MQ 做异步解耦时，怎么保证消息**不丢、也不重复消费（幂等）**？
2. 消息**积压**了（消费者跟不上）你们怎么处理的？
3. 延迟消息、顺序消息、死信队列这些你们在哪些场景用过？

**高频可追问（按实际情况选问）**：
- 不丢（生产者 confirm / 事务、Broker 持久化、消费者手动 ack）？
- 幂等（数据库唯一约束 / 去重表 / Redis 防重 key / 业务状态流转）？
- 积压（扩容消费者、批量消费、临时 topic 中转、死信兜底）？
- 延迟消息（订单关单）、顺序消息（同一分片）、死信（消费失败转移）？

<details>
<summary>标准参考答案</summary>
<p>不丢三环节：生产者端开 confirm（RabbitMQ 发布确认 / Kafka acks=all）并监听失败重发；Broker 端队列 / 主题开启持久化、多副本；消费者端用手动 ack，处理成功再确认，失败不 ack 让消息重投——三者都做才叫可靠投递。</p>
<p>幂等（去重）：同一条消息因重试会重复消费，必须幂等——用数据库唯一约束 / 去重表（消息 id 唯一）、Redis 防重 key（处理前 SETNX 消息 id）、或业务状态流转（已处理则跳过）；订单类用「订单号 + 状态」做幂等最稳妥。</p>
<p>积压治理：先扩容消费者实例 / 增加消费线程，提升单实例消费速度（批量拉取、批量落库）；若短时消费不完，建临时 topic 把消息转移到更多分区多消费者并行消化，消费完再切回；长期积压要查是不是有慢消费（如同步调外部接口超时），优化后再追平。</p>
<p>延迟消息：RabbitMQ 用死信 + TTL 或延时插件，RocketMQ / Kafka 有原生延迟等级——典型场景「订单 30 分钟未支付自动关单」；顺序消息：同一业务 key 路由到同一分片 / 队列保证有序（如订单状态流转）；死信队列：消费多次失败的消息转入死信，人工排查不阻塞主流程。</p>
<p>常见坑：自动 ack 导致丢消息；幂等没做导致重复下单 / 重复扣款；消费者里做同步远程调用拖慢整个队列；消息体过大撑爆 Broker。</p>
</details>

## 第 6 题　微服务治理：注册发现、配置、限流熔断与分布式事务

**题目来源：岗位 JD**（微服务治理，固定题；通用工程场景，不引用候选人旧项目；全部题目不得涉及 AI / 大模型相关内容。本题为「菜单式」综合题，面试官按候选人实际技术栈与现场情况选问 2-4 个小题即可，不必全问）

**问题（菜单式，按实际情况选问）**：
1. 服务注册发现和配置管理你们用的什么（如 Nacos）？给服务加一台实例或改一个配置开关，请求怎么**自动找到新实例、配置怎么动态生效**？
2. 所有请求的入口（鉴权 / 路由 / 限流）在哪一层统一做的（如 Gateway）？
3. 下游服务挂了或者流量突增，你们怎么**限流、熔断、降级**的（如 Sentinel 的三种状态：打开 Open / 半开 Half-Open / 关闭 Closed、fallback）？
4. 跨服务的数据一致性（分布式事务）你们怎么处理（Seata AT/TCC、消息最终一致性、本地消息表）？链路追踪和灰度发布呢？

**高频可追问（按实际情况选问）**：
- Nacos（服务注册发现、配置中心动态生效、健康检查与剔除）？
- Gateway（统一鉴权 / 路由 / 限流，与业务服务解耦）？
- Sentinel 限流熔断（阈值设定、熔断三种状态 Open/Half-Open/Closed、降级 fallback）？
- 分布式事务（Seata AT 自动补偿 / TCC 三阶段 / 消息最终一致性 / 本地消息表）？
- 链路追踪（SkyWalking / Sleuth + Zipkin）、灰度发布（按版本 / 标签路由）？

<details>
<summary>标准参考答案</summary>
<p>注册发现与配置（Nacos）：服务启动时把自身 ip:port 注册到 Nacos，消费者从 Nacos 拉取服务列表做负载均衡调用；实例宕机 Nacos 健康检查剔除，新实例上线自动被发现。配置中心把开关 / 阈值放 Nacos，应用监听配置变更事件，@RefreshScope 或监听回调动态生效，不用重启。</p>
<p>统一入口（Gateway）：所有外部请求先过 Spring Cloud Gateway，在过滤器里做鉴权（校验令牌）、路由转发（按 path / 服务名）、限流（令牌桶 / 计数器）；与业务解耦，业务服务只管业务逻辑，安全与流控在边界统一收口。</p>
<p>限流熔断降级（Sentinel）：限流按 QPS / 线程数设阈值挡住突发流量；熔断用三种状态切换——Closed 正常，错误率超阈值切 Open 直接拒绝并走 fallback 降级，过冷却期进 Half-Open 放少量请求探测，成功则回 Closed 失败续 Open；降级 fallback 返回兜底数据保证主流程可用。</p>
<p>分布式事务：强一致用 Seata AT（自动生成回滚日志补偿）或 TCC（Try-Confirm-Cancel 三阶段，性能好但侵入大）；最终一致常用「本地消息表 / RocketMQ 事务消息」——本地事务和消息表同库写，后台任务投递，消费者幂等处理；选哪种看一致性要求与性能权衡。</p>
<p>可观测与灰度：链路追踪用 SkyWalking / Sleuth + Zipkin，靠 traceId 串起跨服务调用便于排障；灰度发布按版本号 / 标签路由，先把流量放一小部分新版本验证再全量，出错快速切回。</p>
<p>常见坑：注册中心网络分区导致误剔除（用健康探针 + 多副本）；Gateway 限流阈值拍脑袋不设、大促被打爆；分布式事务滥用 Seata 导致性能差，能用消息最终一致就别上强一致；熔断阈值只看错误率忽略慢调用。</p>
</details>
