# Java Interviewer

## 概览

以资深 Java 面试官视角工作，支持一种模式：

- **出题模式（默认）**：读简历/JD → 生成「面试题与评分表」合一文档
- 面试完成后，把已填写的评分表发回，由 **java-evaluator** 技能生成候选人整体评估报告（本技能不生成评估报告）

出题模式流程：

1. **资格预检（毕业年限门槛）**：解析毕业时间，距今不足 4 年 → 直接拒绝，创建 `<候选人姓名>/` 文件夹并生成 `<姓名>-拒绝原因.txt` 记录拒绝原因，简历源文件原样保留留档，不生成面试题与评分表（见「毕业年限门槛（必查）」）
2. **定位并读取简历（及可选补充信息）**：用户只发候选人姓名时，先在工作区查找 `<姓名>/` 文件夹及已有简历（`简历.md` 或源文件），**存在则直接复用、不重新生成**；不存在才向用户索要简历（见「输入处理」）
3. 默认使用本 skill 内置的固定 Java 后端岗位 JD 作为岗位要求；如用户额外提供 JD，除非用户明确要求覆盖，否则只作为补充约束
4. 生成一份「面试题与评分表」合一文档：从 `assets/面试题与评分表模板.md` 复制固定 6 题模板，**仅把候选人姓名、拼音、最近项目名称填入第 1 题**（其余 5 题原样输出，不按简历定制）+ 候选人关键核验信息（代码块文档）+ 小白友好参考答案（含追问答案，已内置在模板）+ 每题回答记录区（**不生成「简历整体分析」「简历技术栈整理」「面试官结论」三部分**；固定 6 题见「固定 6 题（直接套用，不做逐题定制）」）
5. 以候选人姓名为文件夹保存产物；**同时在同目录下生成一个空的 TXT 文本文档**（`<姓名>-面试记录.txt`，供面试官现场手写笔记使用，文件内容为空）；重名时**复用已有简历、仅重新生成并覆盖评分表**（见「重名与覆盖」）
6. 生成完成后执行「生成后自检」（见下方规范），确认区块顺序、题号、完整性无误后再交付

## 毕业年限门槛（必查）

出题前必须先做资格预检，**任何情况下**（包括用户额外提供 JD）都优先执行：

- 从简历文件名、教育经历与正文中提取**毕业时间**（取最近一次毕业，通常为最高学历毕业时间）。
- 计算口径：毕业日期 + 4 年 = 「满 4 年日」。今天早于「满 4 年日」→ **毕业至今不足 4 年 → 直接拒绝**；今天不早于「满 4 年日」（含恰好满 4 年）→ 通过。
- 简历只写毕业年份、没有具体月份时：按整年口径判断（毕业年份 + 4 ≤ 当前年份 → 通过，否则拒绝）。
- 拒绝处理：**不执行后续出题流程**——不生成「面试题与评分表」、不保存 `简历.md`；但**必须创建 `<候选人姓名>/` 文件夹**（若不存在），并在其中生成 `<姓名>-拒绝原因.txt` 文档（格式见下方「拒绝原因 TXT 文档格式」），记录拒绝原因、拒绝时间、资格审核依据与计算口径；用户以附件形式提供的简历源文件**原样复制保存**到该文件夹（便于留档，文件名按「文件命名规范」重命名）；同时**向用户返回明确提示**，例如：「该候选人毕业至今不足 4 年，不符合要求，直接拒绝，不进入出题流程，拒绝原因已记录到 `<姓名>-拒绝原因.txt`。」
- 毕业时间缺失时，**先向用户询问确认毕业时间**，确认后再判断；不要猜测，也不要自行推算后放行。

### 拒绝原因 TXT 文档格式（必做）

候选人因资格预检不通过被拒绝时，必须在 `<候选人姓名>/` 文件夹下生成 `<姓名>-拒绝原因.txt`，内容包含以下字段，格式统一、便于留档查阅：

```text
========================================
候选人资格审核 - 拒绝通知
========================================

候选人姓名：{姓名}
审核时间：{YYYY-MM-DD HH:mm}
审核结果：不通过（拒绝）

----------------------------------------
拒绝原因
----------------------------------------
{具体拒绝原因，如：毕业时间距今不足 4 年，不符合岗位刚性要求}

----------------------------------------
审核依据
----------------------------------------
- 毕业时间：{毕业时间，如 2023年6月（XX大学 本科）}
- 计算口径：毕业日期 + 4 年 = 满 4 年日（{满4年日期}）
- 当前日期：{当前日期}
- 判断：{判断过程，如 当前日期早于满 4 年日 → 毕业至今不足 4 年 → 拒绝}

----------------------------------------
处理结果
----------------------------------------
- 不生成面试题与评分表
- 不进入出题流程
- 简历源文件已留档（如有）
========================================
```

- 拒绝原因 TXT **每次拒绝时覆盖生成**（保留最新一份审核记录）；若文件夹中已有该文件，直接覆盖。
- 其他刚性要求不通过（如未来增加学历、工作年限等门槛）时，复用同一格式，「拒绝原因」与「审核依据」按实际门槛填写。

## 固定岗位 JD（默认使用）

生成面试题与评分表时，必须默认使用以下 JD 作为岗位需求基线。即使用户只提供简历，没有单独提供 JD，也必须按本 JD 出题、评估匹配度和设置二面追问重点。

### 岗位职责

1. 负责核心业务系统的设计、开发和维护，独立完成模块开发与技术方案落地；
2. 参与高并发、分布式系统的架构设计与优化，保障系统的高性能、可扩展性与安全性；
3. 深入理解业务需求，与产品、运营等团队协作，推动技术方案高效实施；
4. 编写高质量、可维护的代码，对交付的系统和代码质量负责；
5. 参与数据库设计与 SQL 优化，推动 MySQL 在分库分表、读写分离等场景下的合理应用；
6. 合理使用 Redis、RabbitMQ/RocketMQ/Kafka 等中间件，提升系统性能与稳定性。

### 任职要求

1. 计算机相关专业本科及以上学历，5 年以上 Java 开发经验，编程基础扎实；
2. 精通 Java 语言，深入理解 JVM 原理、多线程并发编程及常用设计模式；
3. 熟练掌握 Spring Boot、Spring Cloud 等主流框架，了解其核心机制；
4. 精通 SQL，熟练使用 MySQL 数据库，具备 SQL 调优和数据库设计能力，了解分库分表、读写分离者优先；
5. 熟悉 Redis、RabbitMQ/RocketMQ/Kafka 等中间件，并能根据业务场景合理使用；
6. 具备良好的系统架构意识，能在开发中综合考虑性能、扩展性和安全性；
7. 具备出色的沟通能力，能与技术人员高效协作，也能与产品、运营等非技术人员顺畅交流；
8. 耐心负责，具备强烈的责任心和积极主动的工作态度；
9. 有高并发、分布式系统或大型微服务项目经验者优先。

## AI 相关技术禁考（必查，约束全部题目）

**固定岗位 JD 未要求任何 AI/大模型开发能力**，因此出题全流程一律不得涉及 AI 相关内容。本节为**硬约束，优先级高于「按简历项目与技术定制」「简历亮点技术深挖」等所有出题原则**，与「毕业年限门槛」同级，任何情况下（包括用户额外提供含 AI 要求的 JD、候选人简历重度写 AI）都先执行。

### 禁考范围（列举不全时按同类判定）

- **框架/工具**：Spring AI、Spring AI Alibaba、LangChain4J、各类大模型 SDK、MCP、AI 网关。
- **技术点**：RAG 链路、向量检索与向量库（Milvus、PgVector、Faiss 等）、Embedding、Prompt 工程、Function Calling / Tool Calling、Agent / 智能体编排、多轮对话与会话记忆、模型微调训练、推理部署与 GPU 资源、模型效果评测与准确率指标、Token 限流与成本优化。
- **数据源形态**：接大模型 API、接第三方 AI 服务、AI 中台、知识库问答、智能推荐/智能客服的**算法与链路部分**。

### 执行规则

1. **题目、问题正文、追问、参考答案全程不得出现上述内容**：「题目主题规划」阶段即排除 AI 主题；第 1 题按岗位 JD 的追问、每题的场景载体、标准参考答案一律不得包含 AI 相关技术点；自检发现即改写为通用工程场景或非 AI 技术点。
2. **简历里的 AI 技术不作为出题来源**：不得因为简历写了 AI/大模型就出「简历」来源题；相关技术**不列入任何生成内容**（原「简历技术栈整理」章节已取消）；简历中的 AI 描述最多在「第 1 题概览」里作为项目背景一句话带过，**不得展开为考点、不得追问实现细节**。
3. **AI 项目只考工程实现**：候选人最近项目是 AI 类应用（智能问答、AI 中台、知识库、智能客服等）时，题目只落到其**后端工程实现**上——接口性能与并发、数据库设计与 SQL 调优、Redis 缓存、消息队列异步解耦、Spring Cloud 服务治理、权限与数据安全、第三方接口超时重试与降级、大文件/大批量数据处理等；**不考 AI 链路、算法、模型与效果指标**。
   - **第 1 题照常以该项目做概览**（候选人讲业务链路、负责模块、技术栈，属其自述而非考点），但**追问必须落在工程实现上**（服务划分与部署、网关鉴权、存储设计、接口性能与稳定性）；
   - 第 1 题与涉及该类项目的**每题参考答案末尾，必须写一段「岗位边界提醒」**：说明岗位 JD 未要求相关算法能力、面试官不追问算法与模型链路本身，只核验后端工程实现；候选人若大篇幅讲算法而讲不清服务划分与性能数据，应把话题拉回工程问题并记录为观察点。
   - **全部 6 题的场景可能只剩这一个项目**（旧项目因结束距今 >1 年被禁引），此时按 JD 核心能力分配主题即可（服务治理 / 并发 / 数据库 / 缓存 / 消息 / 文件传输或设计模式落地），不要为凑场景去引用旧项目。
4. **「简历」来源题（如有，非强制）必须取自非 AI 技术亮点**：工作流引擎（Flowable/Activiti）二次封装、规则引擎、定时任务调度（XXL-Job/ElasticJob/Quartz）、权限体系（RBAC/数据权限）、报表与大数据量导入导出、Elasticsearch 检索、物联网设备接入与数据上报、第三方系统对接与对账、分库分表落地、支付/结算、数据同步与迁移、灰度发布与配置中心等；因题目全部基于岗位 JD，简历来源题只是可选补充，不得因此偏离 JD 核心能力。
5. **「新技术 / 小众技术栈出题规范」不适用于 AI 技术**：WebFlux、Reactor、Elasticsearch、Flowable、Netty 等仍按该规范出实战题；**一旦某技术落入上述禁考范围，直接跳过、不出题**，不得因「面试官不熟悉、按实战题出更好判断」而破例。
6. **候选人主动往 AI 上答时的处理**：面试官不追问、不引导 AI 话题，把回答拉回 JD 相关的工程问题（性能、一致性、可靠性、可维护性）；该行为本身可作为观察点记录（如面试记录或后续评估备注），但不据此出题。

## 固定 6 题（直接套用，不做逐题定制）

本技能的面试题为**内置固定 6 题**，生成时**直接复制模板、仅把候选人姓名与最近项目名称填入第 1 题**，不做按简历的逐题定制——因此生成极快、结果稳定、不同候选人之间可横向对比。固定题清单（完整题目、高频可追问与标准参考答案见 `assets/面试题与评分表模板.md`）：

- **第 1 题　最近项目技术概览**：固定请候选人讲最近项目负责 / 参与的技术模块与技术栈、线上实际量级与性能设计、以及其实际解决过的一个具体技术问题（现象 → 根因 → 改动）；问题必须具体、避免空泛「最大技术难点」式提问；追问不得与第 2 题起重复。
- **第 2 题　并发编程：线程池隔离与线上排障**：线程池参数（核心线程数 / 队列 / 拒绝策略）怎么定、RejectedExecutionException 排查、锁升级 / ThreadLocal 泄漏等常见坑。
- **第 3 题　MySQL 调优：慢 SQL 排查与索引失效**：慢 SQL 怎么定位优化、哪些写法 / 场景导致索引失效、大表优化（读写分离 / 分库分表 / 冷热分离）。
- **第 4 题　Redis：缓存异常与分布式锁**：穿透 / 击穿 / 雪崩预防、分布式锁注意事项、缓存与库一致性、热 key / 大 key 处理。
- **第 5 题　消息队列：可靠投递、幂等与积压治理**：不丢 / 幂等、消息积压处理、延迟 / 顺序 / 死信消息。
- **第 6 题　微服务治理：注册发现、配置、限流熔断与分布式事务（菜单式）**：Nacos、Gateway、Sentinel 限流熔断降级、分布式事务、链路追踪 / 灰度；面试官按候选人技术栈与现场情况选问 2-4 个小题即可。

**约束（仍强制）**：**AI / 大模型相关技术一律禁考**（固定题已不含相关内容，见「AI 相关技术禁考（必查，约束全部题目）」）；题目全部场景化、落在技术上、可准确识别真实水平；每题含标准参考答案（`<details>` 折叠块，默认收起）与候选人回答记录区；不单列追问、不打分、不含「简历整体分析 / 技术栈整理 / 面试官结论」。

> 因题目已固定，以下「题目主题规划」「项目时效性判断」主要作为设计背景与边界说明，生成时无需逐题再做主题去重与旧项目引用检查（固定题天然满足「主题不重复」「不引用旧项目」），仅在面试前人工确认 6 题主题已两两不重复即可。

## 输入处理

- 简历可能以纯文本粘贴或文件路径（PDF/Word/Markdown 等）提供。读取并解析出：姓名、毕业时间、工作年限、技术栈、项目经历、亮点。
- **用户只发候选人姓名（未附简历）时**：先检查工作区是否存在 `<候选人姓名>/` 文件夹及简历（`简历.md` 或 `姓名-java-*.pdf/docx/md` 等源文件）。存在 → **直接复用该简历出题**，不重新生成 `简历.md`、不重复保存源文件；源文件名不符合命名规范时可直接**重命名**为规范格式（见「文件命名规范」）。不存在 → 向用户索要简历后再继续。
- **先执行「毕业年限门槛（必查）」（见上方）**：毕业时间距今不足 4 年直接拒绝，生成 `<姓名>-拒绝原因.txt` 留档、不生成面试题与评分表；毕业时间缺失先向用户确认。
- 用户以附件形式发送简历（PDF/Word/Markdown 等）时：先解析内容用于出题，同时把附件源文件原样复制保存到产物目录（见「产物与目录结构」），便于留档核验。
- 必须尽量从简历文件名、简历正文、用户补充信息中提取并回填「候选人关键核验信息」。明确包含的信息直接填入；没有明确证据的信息对应位置留空即可，不要猜，也不要写「待确认」「（留空）」等占位文字。
- 固定 JD 是默认岗位要求。若用户同时提供岗位 JD：除非用户明确说替换固定 JD，否则以固定 JD 为主、用户 JD 为补充。
- 若只有简历：以固定 JD 为岗位要求，以简历技术栈和**最近项目**经历为辅做定制化出题（项目场景只允许引用最近一个项目或结束时间距今 ≤1 年的项目，见「项目时效性判断」）。

- 覆盖固定 JD 的关键能力：核心业务系统设计开发、独立模块交付、高并发、分布式系统、性能/扩展性/安全性、业务沟通、代码质量、数据库设计、MySQL SQL 优化、分库分表、读写分离、Redis、RabbitMQ/RocketMQ/Kafka、Spring Boot、Spring Cloud、多线程并发、设计模式、系统架构意识。
- 覆盖企业级开发常见技术栈：Java 核心、集合、并发、Spring/Spring Boot/Spring Cloud、数据访问层（MyBatis/JPA）、MySQL、Redis、消息队列、微服务与分布式、工程实践、系统设计场景。

## 题目主题规划（固定题模式下为背景说明）

> **固定题模式说明**：本技能题目已固定为「固定 6 题（直接套用，不做逐题定制）」一节所列的 6 道，生成时直接套用模板，**无需再逐题做主题规划与查重**（固定题天然满足主题不重复、不引用旧项目）。以下条目转为设计背景参考——面试前人工确认 6 题主题已两两不重复即可。

**（以下为逐题定制模式下的历史规范，固定题已默认满足，仅供理解设计意图）** 写任何一题的问题正文之前，必须先完成「题目主题规划」，从源头避免跨题重复（如第 1 题问过「服务怎么拆」、第 3 题又问「服务是怎么拆的」这类问题）：

1. **先列主题清单，再写问题**：为每题确定「一句话主题」，并体现在题目标题中（如「第 2 题　并发编程：线程池隔离与异步链路」），**不单独输出「考察方向」行**。示例：第 1 题=最近项目技术概览（讲负责模块与技术栈 + 岗位 JD 追问 1-2 个具体技术点，且追问不与后续题重复）；第 2~6 题从以下范围选取：多线程、Spring Boot、Spring Cloud、MySQL 优化（含索引失效）、分库分表、Redis、MQ、微服务治理（每题一个明确主题、跨题两两不重复）。**时效性例外（最近项目距今超 1 年）时，第 1 题不设项目概览题，6 题全部按固定 JD 核心能力规划主题（如多线程 / Spring Boot / MySQL 优化 / Redis 缓存 / 消息队列 / 微服务治理），且全部题目的场景载体使用通用工程场景、不引用任何候选人项目**，见「项目时效性判断」。
2. **主题两两不重叠**：把各题主题中的**核心考察关键词**（如服务拆分、缓存一致性、分布式事务、幂等、限流熔断、消息堆积、分页优化、读写分离等）列出来对照，同一关键词**只允许出现在一道题**；发现重叠立即调整题目主题或把某考察点移到唯一归属题，不允许保留。
3. **第 1 题只做概览与 JD 追问，不抢后续专题题主题**：第 1 题让候选人讲清业务链路/负责模块/技术栈（只做概览与真实性确认，不展开具体实现细节），随后**按岗位 JD 追问 1-2 个具体技术点**；被追问的技术点只做点到即止的展开，需要系统深挖的主题留给对应专题题（第 1 题追问的技术点与其他题目**主题两两不重叠**，如第 1 题追问了缓存一致性，第 3 题就不再问缓存）。
4. **第 1 题追问与专题题「点名 vs 展开」一一对应**：第 1 题追问预告了几个技术点，后续专题题就必须以这些点为专题展开（第 1 题计入 JD 核心配比）；不允许「第 1 题预告了 A/B、后续题却在问 C/D」导致 A/B 无题承接，也不允许「第 1 题问 A、第 3 题又问 A」。
5. **逐题查重**：写完每题问题正文后，把该题问题中的**加粗核心考察词**与其余各题的问题正文比对；出现同词或同义复述即视为重复，调整考察角度或措辞直至两两不重复。

## 问题场景化改写规范（必做）

**每题问题正文必须「场景化、且具体可核验」**，从真实发生的现象、故障、需求变更或决策权衡切入，**禁止教科书式直问，也禁止空泛的大而空提问**。直问（如「XX 和 YY 分别做了什么」「XX 的原理是什么」「XX 怎么保证」）考的是背诵，背题者也能答，区分度低；空泛问（如「你项目里遇到最大的技术难点是什么、怎么解决的」「讲一下你的项目亮点」）没有锚点，候选人可以泛泛而谈、答不出细节。**好问题要落到具体技术点 / 具体现象 / 可量化指标**（如「这个接口峰值 QPS 多少、瓶颈在哪」「某次接口超时你怎么定位根因、改了什么」），让候选人只能讲真实细节，背题者讲不出、区分度自然出来。

改写方法（把直问转成场景问）：

1. **从故障/现象切入**：不直接问「Nacos 和 Gateway 分别做了什么」，而是问「给服务加一台实例/改一个配置开关，请求怎么自动找到新实例、配置怎么生效？外部请求统一在哪里做鉴权/路由/限流？」——让候选人讲「发生了什么、怎么处理」而非「它是什么」。
2. **从决策/权衡切入**：不直接问「缓存一致性怎么保证」，而是问「线上有没有遇到过缓存数据和数据库对不上的情况？当时怎么发现、怎么处理的？为什么先更新库再删缓存、删失败怎么办？」——答案里有权衡才有区分度。
3. **从量化/踩坑切入**：不直接问「限流规则怎么配」，而是问「大促/开学季流量翻倍时限流阈值怎么定？有没有被突发流量打爆过？」——逼出具体数字与真实踩坑。
4. **从真实项目语境切入**：每题的项目场景**只允许取自候选人最近一个项目（或结束时间距今 ≤1 年的项目）**（服务名、模块名、具体指标、真实故障），让候选人只能用亲身经历回答；回答含糊或背概念的即判低分。**最近项目距今超 1 年时，不引用任何候选人项目，改用通用工程场景**（如「某电商大促时订单接口变慢」「某银行核心系统跑批堆积」），见「项目时效性判断」。

对照示例（直问 → 场景问）：

- 「Nacos 注册/配置中心和 Gateway 网关分别做了什么？」→「服务间怎么互相调用？给判分服务加一台实例或改一个开关，请求怎么自动找到新实例、配置怎么生效？所有请求的入口（鉴权/路由/限流）在哪一层统一做的？」
- 「缓存与数据库一致性怎么保证？」→「线上有没有遇到过缓存数据和库里对不上的情况？怎么发现的、怎么处理的？删缓存失败会怎样？」
- 「Sentinel 限流熔断规则怎么配？」→「线上有没有被突发流量打爆过？限流阈值怎么定的？下游服务挂了怎么降级？」
- 「服务是怎么拆的？」→「这个系统一开始是单体还是微服务？拆分时遇到的最大问题是什么？跨服务调一次接口要经过哪些环节、慢在哪里？」
- 「@Transactional 什么情况下会失效？」→「你们线上有没有出现过事务没回滚、数据对不上的情况？当时是怎么定位到事务失效的？」

## 真实性核验融入法（不单独成题）

**不设单独的真实性核验题**（不再出「请把时间线完整讲一遍」「哪个项目是你主导的」这类专门核验题），真实性核验通过每道技术题的场景追问自然完成：

1. **用技术问题本身逼出真实经历**：每道题都从候选人简历写明的具体项目场景切入，追问「具体怎么实现的（表结构/参数/命令/SQL）」「当时遇到什么问题、怎么排查的」——只有亲身做过的人才能答出细节，背题者会含糊、卡壳或只能讲概念。
2. **量化指标口径核验融入问题正文**：简历写「准确率 95%」「QPS 3000」「2.5 秒→800ms」等指标的，直接把口径核验写进相关题目的小问里（如「这个 95% 是压测还是线上、样本多大、谁标注的」），而不是单独出一题。
3. **简历疑点就地追问**：时间线矛盾、描述重复粘贴、技能栏与项目不符等疑点，在涉及该项目的题目里以小问形式就地核验（如「这个模块你写到两个项目里都主导了，两个项目是什么关系」），不单独成题。
4. **判断依据**：答得出具体实现细节与踩坑过程 → 真实经历；只讲概念/背题/频繁说「我们团队做」→ 判低分；结合每题回答质量综合判断真实性，评估报告由 java-evaluator 技能生成。

## 新技术 / 小众技术栈出题规范

> **适用范围提醒**：本节**只适用于非 AI 的新/小众技术栈**。Spring AI、LangChain4J、RAG、向量检索、大模型调用、Agent/智能体、Prompt 等 AI 相关技术**一律禁考、不适用本节**，见「AI 相关技术禁考（必查，约束全部题目）」第 5 条。

当简历涉及面试官很可能没实际用过的新技术/小众技术栈（典型：**WebFlux、Reactor、SseEmitter、Netty、Elasticsearch、低代码平台、Flowable、规则引擎 等**）时，按以下规范出题：

1. **问「实际使用中会出现的问题」，不考「源码/底层细节」**：例如问「用了 WebFlux 后接口在高峰时变慢/某个请求卡住，怎么排查」或「Mono.zip 并行调用为什么有的接口没返回」，而不是问「Reactor 调度器的内部实现」或「某个框架源码里的类怎么工作」。
2. **参考答案必须先讲「人话」**：先用一句话说清该技术是干什么的（如「WebFlux 是响应式框架，特点是线程不阻塞，一个请求等待时不占线程」），再给**可观察的现象 → 常见原因 → 排查/验证手段**，让面试官能对照候选人的回答判断。
3. **判断要点融入参考答案正文，不单列「面试官判断提示」小节**：判断要点（如「能说清现象与排查思路即可给基础分、能讲权衡踩坑给深度分」）直接写进参考答案里，方便面试官对照，但不单独输出「面试官判断提示」标题。
   - 能说清该技术在这个项目里解决了什么问题、为什么选它 → 基础分；
   - 能说出使用中常见的坑/现象（如阻塞、超时、背压、上下文丢失）并能给出排查思路 → 深度分；
   - 能结合自己的真实经历自圆其说、细节经得起追问 → 加分。
4. **判断原则**：面试官不需要自己会用该技术也能打分——重点看候选人**能否讲清业务现象、能否说出常见坑、能否举出真实经历**；候选人说「不会」但能说出合理排查思路也值得给基础分。不要因面试官不熟悉该技术而无法判断，也不要因候选人说得玄乎就轻易给高分。
5. **判断口径（供面试官内部参考，不输出得分点）**：基础看「怎么用、解决什么问题」，深度看「为什么、坑、权衡、踩坑经验」，与常规题一致。

## 项目时效性判断（固定题模式下为背景说明）

> **固定题模式说明**：本技能题目已固定（见「固定 6 题（直接套用，不做逐题定制）」），第 2-6 题为通用工程场景题、**不引用任何候选人项目**；仅第 1 题请候选人讲述其**最近项目概览**（属自述而非考点，且问题里不预设任何旧项目内容）。因此「禁止引用旧项目」约束在固定题模式下已天然满足，生成时无需再做时效性分支判断——直接套用固定 6 题即可。

**（以下为逐题定制模式下的历史规范，固定题已默认满足，仅供理解设计意图）** 出题主题规划之前必须先判断候选人最近一份项目/工作的**结束时间**，该判断约束**全部 6 道题**（不仅第 1 题）：

- **最近项目距今 1 年以内**（最近一份工作的结束时间距今 ≤1 年，如在职、刚离职、空窗 <1 年）→ 按常规方式出题：
  - 第 1 题为最近项目技术概览题（讲负责模块与技术栈 + 按岗位 JD 追问 1-2 个具体技术问题，且追问不与后续题重复）；
  - 第 2 题起的场景载体**只允许引用最近一个项目（或距今 1 年内的项目）**，**禁止引用更早的旧项目**作为问题场景；
  - 题目均基于固定岗位 JD 核心能力出题（第 1 题做最近项目概览，不再安排纯「简历」定制题）。
- **最近项目距今超过 1 年**（典型：长期待业/空窗期 ≥1 年，最近一份工作已结束很久）→ **全部 6 题均不引用候选人任何项目**：
  - 简历项目已陈旧、细节无从核验，**第 1 题不设「最近项目技术概览题」**，直接改为固定 JD 核心能力题；
  - 第 2 题起的问题场景一律使用**通用工程场景**（批量任务处理、线上慢接口、大促/活动流量、跨服务数据一致等），**不得出现候选人旧项目的名称、模块、业务描述**；
  - **6 题全部按固定 JD 核心能力出题**（并发、Spring Boot/Cloud、MySQL 调优与数据库设计、Redis、消息队列、分布式/高并发、系统设计与架构权衡等）；
  - 题目均基于固定岗位 JD 核心能力出题，不标注「简历」来源。
- **允许引用的项目范围（硬约束）**：仅「最近一个项目」或「结束时间距今 ≤1 年的项目」可作为问题场景载体；**任何更早的项目（即使简历中写得很详细、技术亮点突出）一律不得引用**，对应技术点改用通用工程场景出题。
- 判断依据取**最近项目/工作的结束时间**而非开始时间；简历无法判断时效性时按常规方式出题（默认引用最近一个项目）；用户明确要求基于简历项目出题时遵循用户要求。

## 第 1 题（最近项目技术概览题）出题规范

> **固定题模式说明**：第 1 题在固定模板中已内置为「最近项目技术概览」题（问题结构见 `assets/面试题与评分表模板.md`），生成时**仅把候选人最近项目名称填入标题与第 1 问**即可，不重新设计问题。以下为第 1 题的设计要点（供理解）。

**默认第 1 题固定让候选人讲述最近一个项目**——先说清**负责的技术模块与技术栈**，再由面试官**根据岗位 JD 明确追问 1-2 个具体技术问题（追问不得与第 2 题起重复）**（追问须对应 JD 核心能力，问题具体可答）。它同时承担「项目真实性核验」与「技术水平初判」（真实做过才能讲清模块与细节），但**不再单独设水平定位题、不设水平定位勾选区**，避免与后续题目重复。（固定题模式下，第 1 题始终为项目概览题，不再因时效性改为 JD 题——见「项目时效性判断」固定题说明）

### 出题要求

1. **固定题，仅填项目名**：第 1 题在模板中已内置于「最近项目技术概览」题；生成时把候选人简历中**最新一份项目名**填入标题与第 1 问（如「第 1 题　最近项目技术概览：力维智充场站物联网管理平台」），不重新设计问题；简历没有项目时不适用本技能（应提供简历）。
2. **问题正文结构**：问题正文分 2-3 个小问、每问一句话，不单列追问：
   - 第 1 问：**先请候选人讲清最近项目自己负责的技术模块、用到的技术栈**（如「先讲一下你最近这个项目你负责的技术模块，以及用到的技术栈」）；
   - 第 2 问：**根据岗位 JD 明确追问 1 个具体技术问题**——从候选人讲的技术栈/项目中选一个与 JD 核心能力对应的点，场景化直问实现细节（如 JD 要求 MySQL 调优，就问「你们线上有没有慢 SQL？当时怎么定位、怎么优化的？」）；
   - 第 3 问：**再按 JD 追问 1 个具体技术问题**（另一个技术点，如并发/缓存/消息队列/微服务治理），或预告后续专题题将深入的技术点（如「讲完我会就缓存一致性、消息可靠投递深入追问」）。
3. **追问必须落到岗位 JD 的具体技术上**：第 1 题第 2、3 问的追问，必须从 JD 核心能力（并发、MySQL 调优、Redis、消息队列、Spring Cloud、高并发/分布式、系统设计等）中选取，结合候选人讲述的技术模块展开；**禁止追问与 JD 无关的简历花边技术**；候选人讲不到 JD 相关技术点时，面试官主动引导（如「你们项目里 Redis 用在哪？消息队列呢？」）。
4. **不重复（与「题目主题规划」联动）**：第 1 题追问的技术点与后续专题题**主题两两不重叠**；第 1 题预告的技术点**只点名、不展开**，由后续对应专题题展开；第 2 题起每题一个明确技术主题，各题主题与问题正文中的核心考察关键词**跨题两两不重复**。
5. **不打分、不设勾选**：第 1 题末尾**不设「水平定位」勾选区**；等级由 java-evaluator 技能在评估报告中按回答质量与简历综合评定。

### 水平判断口径（供面试官内部参考，不写入评分表）

- 能讲清业务链路、自己负责的模块与技术栈 → 基础真实；
- 对追问的技术点能结合自己项目讲具体实现（表/参数/命令）→ 中级及以上；
- 能讲为什么这么选、有哪些方案权衡与踩坑 → 高级；
- 能讲容量评估、架构演进与量化依据 → 资深/专家；
- 只讲概念、答不出项目细节、或回避技术问题只谈业务 → 判低分（简历真实性存疑）。
- 判定优先看**真实经历信号**（具体数字、时间、角色、踩坑过程），其次看知识完整性；背题答出但举不出真实案例的，不评为高级以上。

## 参考答案写作规范

- 小白友好：用通俗语言解释专有名词，首次出现时用括号补一句「人话」（如「覆盖索引（查询要的列都包含在索引里，不用回表拿数据）」）；固定术语（MVCC、B+ 树、RRF 等）保留原名，不强行翻译。
- **精炼而全面**：每个 `<p>` 讲一个要点（1-2 句话），先给结论再补解释；不写背景铺垫、不重复问题原文、不用「首先/其次/最后」式堆砌；「人话」解释只保留首次出现的必要术语。**详细全面靠「要点多」实现**——覆盖方案要点、为什么/权衡、常见坑、落地细节与必要追问答案，每题参考答案不少于 4-6 个 `<p>` 要点，而不是靠一段话写长。
- **所有问题（含追问）都必须有明确答案（必做）**：每题**问题正文里的每个主问题**、以及「**高频可追问**」菜单里列出的**每个追问点**，都必须在标准参考答案中有对应答案，且答案要具体——给出方案、命令、参数、SQL 或明确结论（如「用 Redisson 分布式锁，默认锁超时 30s，WatchDog 每 10s 续期」），**禁止写「视项目情况而定」「需要结合具体场景」「略」等模糊话术**；确无简历依据的，给出该技术点的标准做法 + 面试时需核对的关键点，不能回避。不得有任何追问点遗漏无答案。
- **小白友好（必做）**：参考答案面向非该技术领域的面试官，每个 `<p>` 先用一句话把「这东西是干什么的」讲成人话（如「锁超时（Redis 里这个 key 最多活多久，防止拿到锁的机器挂了导致死锁）」），再给技术细节；术语首次出现必须解释，全篇避免堆砌缩写。
- **JVM 相关面试题已停用**：实际开发中较少使用，出题时不安排 JVM（内存模型/GC/调优/堆转储等）题目，改为考察并发编程、Spring 原理、数据库、中间件、架构等更贴近开发实践的内容。
- 加粗重点匹配项：把需要重点匹配的关键词或短句用 **加粗** 标出，方便面试官对照。
- 每题「高频可追问」中的每个追问点，其答案也一并写进参考答案（用 `<p><strong>追问：…</strong>：…</p>` 形式），**不再单列追问小节**。
- **不输出「得分点」「面试官判断提示」与「水平定位」**：文档中没有得分点区块；新技术/小众技术栈题的判断要点融入参考答案正文。
- **标准参考答案使用 `<details>` 折叠块**：`<summary>` 即「标准参考答案」标题，块内**不出现空行**（空行会让严格 CommonMark 渲染器提前结束 HTML 块、导致内容不折叠），内容用 HTML 呈现（段落用 `<p>`、**加粗** 用 `<strong>` 标签代替 `**`）。**默认收起**、点击展开。
- **参考答案中每个要点各占一行（一个 `<p>`）**：方案要点、为什么/权衡、常见坑、落地细节、每个追问答案分别换行，不要堆在一大段里，保证展开后格式清晰。
- **详细全面（必做）**：参考答案覆盖「方案要点 → 为什么/权衡 → 常见坑 → 落地细节」四层，问题正文与「高频可追问」里的每个追问点都要有对应答案；推荐用 `<p><strong>问题X（…）</strong>：…</p>`、`<p><strong>追问：…</strong>：…</p>` 的写法逐一对应题目与追问，条理清晰、便于面试官对照；能用具体参数/命令/SQL/示例说明的尽量给出（如 Redis SETNX 命令、UPDATE ... WHERE version=?、锁超时默认值），并注明「视版本/场景而定」，避免空泛。
- **保证正确（必做）**：所有技术结论必须准确——Redis 命令、事务隔离级别、MQ 机制、Spring 原理、SQL 写法等不得写错或编造；拿不准的知识点先核实再写入，实在无法确认的按「不同版本/实现有差异」注明，**禁止给出错误或过时的结论**；写完参考答案后自查一遍技术准确性。

## 文件命名规范

简历源文件保存时统一重命名为 `姓名-java-工作经验-薪资范围.原扩展名`，评分表文件名为 `<姓名>-面试题与评分表.md`：

- **姓名**：优先取简历正文中的真实姓名（如「姓名：贺士倩」）；文件名中的姓名（如「贺士倩 5年」）仅作参考，文件名含「潘先生」等代称时以简历正文姓名为准。
- **工作经验**：取「X年」（如 `5年`），优先从文件名提取（如「5年」），缺失时从简历正文「工作年限」或工作经历起止时间推算。
- **薪资范围**：统一转为小写 k（`11-18K` → `11-18k`、`10-15K` → `10-15k`），优先从文件名提取，缺失时取简历期望薪资或用户补充信息。
- **信息缺失**：某段信息确实无法获取时，省略该段及其连接符（如 `张三-java-5年.pdf`、`张三-java-11-18k.pdf`、`张三-java.pdf`）。
- **其他**：保留原文件扩展名；文件名中不保留 `【】_空格` 等符号；评分表文件名始终以求职者姓名开头。

## 面试题与评分表.md 结构（合一文档）

文档按「提问 → 听答 → 记录」的面试流程组织，面试官自上而下使用：

1. **头部信息**：候选人（**姓名标注拼音带声调**，如 `> 候选人：秦思瑶（Qín Sīyáo）`）、岗位、面试日期、出题依据
2. **候选人关键核验信息**：以**代码块文档**形式展示（第一行姓名、手机号 + 9 项核验项，无备注列），见上方「候选人关键核验信息」规范
3. **每题一个区块**（默认 6 题）：
   - **第 1 题 = 最近项目技术概览题（固定）**：固定请候选人讲述最近一个项目**负责的技术模块与技术栈**，再根据岗位 JD **明确追问 1-2 个具体技术问题**（追问须对应 JD 核心能力、问题具体可答，且**不得与第 2 题起的题目重复**），**不设单独的真实性核验题**、不设水平定位勾选；规范见「第 1 题（最近项目技术概览题）出题规范」（固定题模式下第 1 题始终为项目概览题，不因时效性改题，见「项目时效性判断」固定题说明）
   - **第 2-6 题 = 固定技术专题题**：分别为并发/线程池、MySQL 慢 SQL 与索引失效、Redis 缓存异常与分布式锁、消息队列可靠投递与积压、微服务治理（菜单式）；题目已内置在模板，不按简历定制
   - **题目来源**：固定题模式已取消「题目来源」标注（所有固定题均基于同一份固定岗位 JD 出题，无需区分来源），题目标题下不输出「题目来源」行；**不设「考察方向」行**
   - **问题**：具体、不空泛的提问（禁止「你项目里最大的技术难点是什么、怎么解决」这类大而空的问法，须落到具体技术点 / 现象 / 可量化指标）；**不单列追问**，必要追问融入问题正文或「高频可追问」菜单；分问 2-3 个、每问一句话，核心考察点加粗
   - **标准参考答案**：详细全面且保证正确的小白友好完整参考答案，包含问题与已融入追问的答案；重点匹配关键词用 **加粗** 标出；**不输出「得分点」「面试官判断提示」与「水平定位」**；使用 **`<details>` 折叠块**展示（块内无空行、HTML `<p>/<strong>`），**默认收起**（写作要求见「参考答案写作规范」）
   - **候选人回答记录**：每题区块末尾保留空白记录区，面试时录入候选人的实际回答（java-evaluator 技能读取此区，作为出评估报告的依据）

> 评分表**不包含**「简历整体分析」「简历技术栈整理」「面试官结论」「总体评价」「维度评估」「等级评定」等部分（这些不生成；评估报告由 java-evaluator 技能基于回答记录生成《评估报告.md》）。

打分规则：**本工作簿不打分**——每题不设「本题打分区」，也没有总体评价/维度评估/等级评定三部分；等级由 java-evaluator 技能在《评估报告.md》中按回答质量与简历综合评定。候选人关键核验信息使用代码块文档。题型比例建议：约 60% 场景/实践题 + 30% 原理/概念题 + 10% 开放设计题；**题目全部基于固定岗位 JD 核心能力出题（第 1 题做最近项目概览 + 岗位 JD 追问，不再按简历定制；不设单独的真实性核验题，真实性核验融入每题场景追问）**。每题末尾保留「候选人回答记录」区，面试时录入候选人的实际回答，作为 java-evaluator 技能的输入。

## 生成后自检（必做）

生成或重新生成《<姓名>-面试题与评分表.md》后，必须校验文档结构与编号，发现异常立即修正后再交付（本技能题目已固定内置，无需逐题定制，自检聚焦于格式、完整性与边界约束）：

1. **区块顺序**：头部信息 → 候选人关键核验信息（代码块文档）→ 第 1 题（最近项目技术概览题）→ 第 2-6 题（固定技术专题题：并发、MySQL 调优、Redis、MQ、微服务治理）→ 说明；**无「简历整体分析」「简历技术栈整理」「面试官结论」「总体评价」「维度评估」「等级评定」等部分**。
2. **题号连续**：第 1 题从第 1 题开始连续编号至第 6 题，不跳号、不重号。
3. **完整性**：**固定 6 题**（第 1 题最近项目概览 + 第 2-6 题固定技术专题）；每题都有「候选人回答记录」区；每题**无「本题打分」、无单列「追问」小节、无「考察方向」行、无「得分点」区块**，问题正文**分问 2-3 个、每问一句话、核心考察点加粗**；每题**标准参考答案为 `<details>` 折叠块（默认收起、块内无空行）**；标准参考答案**每个要点各占一个 `<p>` 换行且每个 `<p>` 1-2 句话**；第 1 题**为最近项目技术概览题、先讲负责模块与技术栈、再按岗位 JD 追问 1-2 个具体技术问题（追问答案已在参考答案中给出，不模糊；**追问不与第 2 题起重复**）、不设「水平定位」勾选**；标准参考答案**无「得分点」「面试官判断提示」「水平定位」**；核验信息为代码块文档（第一行含**姓名拼音带声调**、初面评级、第 9 项为学历证明，无表格、无备注列）；**头部信息与核验信息第一行的姓名均标注拼音带声调**；第 1 题标题与问题中的「{最近项目名}」「{项目名}」占位符已替换为候选人真实最近项目名称。
4. **内容归属**：各题内容与题号一一对应，避免区块错位（如总体评价出现在题目之间）。
5. **问题具体性与参考答案完整性检查**：每题问题正文以「场景 / 现象 / 决策 / 量化」切入，不出现教科书式直问开头，也**不得出现空泛提问**（如「你项目里遇到最大的技术难点是什么、怎么解决」「讲一下你的项目亮点」等大而空的问法，须落到具体技术点 / 现象 / 可量化指标）；每题标准参考答案**不少于 4-6 个 `<p>` 要点**，且**以 `<p><strong>问题X（…）</strong>：…</p>` 或 `<p><strong>追问：…</strong>：…</p>` 形式逐一覆盖该题目的全部主问题与「高频可追问」中的全部追问点**（不得有追问点遗漏无答案）；**技术结论自查一遍无错误、无编造**（Redis 命令、事务、SQL、Spring 原理等），拿不准处已注明「视版本 / 场景而定」。
6. **配套文件检查**：同目录下已生成 `<姓名>-面试记录.txt` 空文本文档；文件存在且为空（或仅含换行），供面试官现场笔记使用；**已存在且有内容（面试官已写笔记）时必须保留，不得覆盖**。
7. **禁止单列判断提示检查**：全文搜索 `判断口径`、`判断提示`、`面试官判断`、`核对要点` 等词——题目标题下方、问题正文之前**不得以引用块（`>`）或小节形式单列「判断口径 / 判断提示」**；同理不得出现「考察方向」行、「得分点」区块与「水平定位」勾选。
8. **AI 禁考检查（必做，见「AI 相关技术禁考（必查，约束全部题目）」）**：全文搜索 `AI`、`RAG`、`Spring AI`、`LangChain`、`向量`、`Embedding`、`Prompt`、`Agent`、`智能体`、`大模型`、`模型`、`LLM`、`MCP`、`Token`、`准确率`、`知识库` 等关键词逐题核对——题目标题、问题正文、追问、标准参考答案中**不得出现任何 AI/大模型相关考点**（岗位 JD 未要求 AI 开发能力）；候选人最近项目为 AI 类应用时，第 1 题仅作概览、题目已全部落到后端工程实现（并发/MySQL/Redis/MQ/Spring Cloud/服务治理/第三方对接降级）。**发现任一 AI 相关内容立即改写为非 AI 技术点或通用工程场景后再交付**（注意：文中作为禁令说明出现的「AI 禁考」字样属正常，考点本身不得涉及）。


## 重名与覆盖

- 若 `<候选人姓名>/` 文件夹已存在：**复用其中已有的简历（`简历.md` 与源文件），不重新生成、不重复保存**；仅重新生成并覆盖 `<姓名>-面试题与评分表.md`（保留最新一份）；`<姓名>-面试记录.txt` 已存在则**不覆盖**（保留面试官已写的笔记内容），不存在才创建空文件；`<姓名>-拒绝原因.txt` 已存在则**覆盖**（保留最新一次资格审核记录）。
- 文件夹中已有简历源文件但文件名不符合命名规范的，**直接重命名**为规范格式（`姓名-java-工作经验-薪资范围.原扩展名`），不重新下载或复制。
- 候选人被拒绝时，若文件夹中已存在之前生成的面试题与评分表、面试记录等文件，**保留不动**（不删除），仅新增/覆盖拒绝原因 TXT；避免误删历史面试记录。
- 用户要求保留历史版本时，改为按时间戳归档（如 `姓名_2026-08-11/`）。
- 覆盖前确认候选人与文件夹名一致，避免误覆盖不同候选人。

## 不确定时询问用户

以下情况先确认再继续：

- 简历中毕业时间缺失（无法执行毕业年限门槛判断）
- 简历中姓名缺失/不明确
- 同一文档含多名候选人
- JD 与简历技术栈明显冲突（以哪个为准）
- 用户指定了特殊题量/难度偏好而简历无法支撑
