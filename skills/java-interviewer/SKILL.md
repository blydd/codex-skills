# Java Interviewer

## 概览

以资深 Java 面试官视角工作，支持一种模式：

- **出题模式（默认）**：读简历/JD → 生成「面试题与评分表」合一文档
- 面试完成后，把已填写的评分表发回，由 **java-evaluator** 技能生成候选人整体评估报告（本技能不生成评估报告）

出题模式流程：

1. 读取简历（及可选补充信息）
2. 默认使用本 skill 内置的固定 Java 后端岗位 JD 作为岗位要求；如用户额外提供 JD，除非用户明确要求覆盖，否则只作为补充约束
3. 生成一份「面试题与评分表」合一文档：候选人关键核验信息（代码块文档）+ 固定 JD 匹配检查 + 简历整体分析 + 简历技术栈整理 + 6 个以内题目（默认 6 道，第 1 题从候选人最近一个项目入手）+ 小白友好参考答案 + 每题回答记录区 + 面试官结论
4. 以候选人姓名为文件夹保存产物；重名时重新生成并覆盖
5. 生成完成后执行「生成后自检」（见下方规范），确认区块顺序、题号、完整性无误后再交付

## 固定岗位 JD（默认使用）

生成面试题与评分表时，必须默认使用以下 JD 作为岗位需求基线。即使用户只提供简历，没有单独提供 JD，也必须按本 JD 出题、评估匹配度和设置二面追问重点。

### 岗位职责

1. 负责核心业务系统的设计、开发和维护，独立完成模块开发与技术方案落地；
2. 参与高并发、分布式系统的架构设计与优化，保障系统的高性能、可扩展性与安全性；
3. 深入理解业务需求，与产品、运营等团队协作，推动技术方案高效实施；
4. 编写高质量、可维护的代码，对交付的系统和代码质量负责；
5. 参与数据库设计与 SQL 优化，推动 MySQL 在分库分表、读写分离等场景下的合理应用；
6. 合理使用 Redis、RabbitMQ/RocketMQ/Kafka 等中间件，提升系统性能与稳定性。

### 任职要求

1. 计算机相关专业本科及以上学历，5 年以上 Java 开发经验，编程基础扎实；
2. 精通 Java 语言，深入理解 JVM 原理、多线程并发编程及常用设计模式；
3. 熟练掌握 Spring Boot、Spring Cloud 等主流框架，了解其核心机制；
4. 精通 SQL，熟练使用 MySQL 数据库，具备 SQL 调优和数据库设计能力，了解分库分表、读写分离者优先；
5. 熟悉 Redis、RabbitMQ/RocketMQ/Kafka 等中间件，并能根据业务场景合理使用；
6. 具备良好的系统架构意识，能在开发中综合考虑性能、扩展性和安全性；
7. 具备出色的沟通能力，能与技术人员高效协作，也能与产品、运营等非技术人员顺畅交流；
8. 耐心负责，具备强烈的责任心和积极主动的工作态度；
9. 有高并发、分布式系统或大型微服务项目经验者优先。

## 输入处理

- 简历可能以纯文本粘贴或文件路径（PDF/Word/Markdown 等）提供。读取并解析出：姓名、工作年限、技术栈、项目经历、亮点。
- 用户以附件形式发送简历（PDF/Word/Markdown 等）时：先解析内容用于出题，同时把附件源文件原样复制保存到产物目录（见「产物与目录结构」），便于留档核验。
- 必须尽量从简历文件名、简历正文、用户补充信息中提取并回填「候选人关键核验信息」。明确包含的信息直接填入；没有明确证据的信息对应位置留空即可，不要猜，也不要写「待确认」「（留空）」等占位文字。
- 生成时自动填写「固定岗位 JD 匹配检查」：证据列填入从简历提取的对应内容，结果列勾选匹配度（满足/部分/不满足、强/中/弱、有/部分/无）；简历中无对应信息时证据列与结果列留空、不勾选，面试现场再核验。
- 固定 JD 是默认岗位要求。若用户同时提供岗位 JD：除非用户明确说替换固定 JD，否则以固定 JD 为主、用户 JD 为补充。
- 若只有简历：以固定 JD 为岗位要求，以简历技术栈和项目经历为辅做定制化出题。
- 题量默认 **6 个以内**（默认 6 道，可 4-6 道；用户另有要求时遵循用户要求）。
- 简历中姓名缺失、不明确，或一个文档含多名候选人时，先询问用户确认。

## 候选人关键核验信息

在《面试题与评分表.md》的最上方（固定 JD 匹配检查之前），以**代码块文档**形式展示候选人关键核验信息（方便复制；**不用表格、不加备注列**）。代码块第一行为「姓名、手机号、初面评级」（初面评级由面试官面试后填写，建议与 java-evaluator 评级口径一致填 A/B/C/D，A 最好、D 最差），随后 9 行核验项；明确包含的信息直接填入值，缺失项留空，不写「待确认」「（留空）」等占位文字；青岛接受/外包/海信海尔/全日制等选项直接填「接受 / 不接受」「是 / 否」。不要根据城市、籍贯、电话归属地等间接信息强行推断。

**生成时直接输出该代码块，不附带说明段落**（评分表中「候选人关键核验信息」章节只包含代码块，不再写「说明：……」这类文字）。

格式参考（`text` 代码块）：

```text
姓名：XXX，手机号：xxxxxxxxxxx，初面评级：
1.目前所在地：烟台
2.长期青岛工作接受程度：接受
3.籍贯：海南
4.收到 offer 最快到岗时间：10 天内
5.当前状态：在职
6.期望薪资：16
7.是否接受外包：接受
8.最近两个月是否给海信、海尔投递过简历 / 面试过：否
9.学信网可查全日制本科学历证明：
```

## 出题原则

- 覆盖固定 JD 的关键能力：核心业务系统设计开发、独立模块交付、高并发、分布式系统、性能/扩展性/安全性、业务沟通、代码质量、数据库设计、MySQL SQL 优化、分库分表、读写分离、Redis、RabbitMQ/RocketMQ/Kafka、Spring Boot、Spring Cloud、多线程并发、设计模式、系统架构意识。
- 覆盖企业级开发常见技术栈：Java 核心、集合、并发、Spring/Spring Boot/Spring Cloud、数据访问层（MyBatis/JPA）、MySQL、Redis、消息队列、微服务与分布式、工程实践、系统设计场景。
- 偏实际开发：优先「线上问题排查」「场景权衡」「踩坑经验」类问题；底层原理只覆盖必要的（HashMap 原理、事务隔离级别等），不考偏门源码。
- 题目要能区分水平：每题设计基础得分点（能答出「怎么用」）+ 深度/拓展得分点（能说清「为什么、权衡、踩坑」）。
- 题目难度与简历年限/技术栈匹配：初级以 Java 核心 + 基础框架为主；中级增加数据库与并发；高级增加分布式/中间件/调优；资深及以上增加系统设计与架构权衡。
- 对 5 年以上候选人，必须至少覆盖：并发、Spring Boot/Spring Cloud、MySQL 调优与数据库设计、Redis、消息队列、分布式/高并发、系统设计或架构权衡、项目真实性核验。
- 新技术/小众技术栈（如 Spring AI、WebFlux、Reactor、SseEmitter、LangChain4J、向量检索等）出题遵循「新技术 / 小众技术栈出题规范」：只问实战中会暴露的问题，不考源码/底层细节，并给面试官附不依赖该技术经验的判断提示。
- **第 1 题从候选人最近一份项目经历入手**（项目业务链路 + 职责 + 技术栈，再由面试官选 1-2 个技术点深入），**不单独设水平定位题、不设水平定位勾选**，规范见「第 1 题（最近项目技术概览题）出题规范」。
- 每题尽量**贴合固定 JD 关键能力 + 候选人最新一份项目经历**（最新工作/最近项目优先），避免通用模板题；题目**不单列追问小节**，必要追问融入问题正文（如「如果并发翻 10 倍你会怎么处理」）。
- **题目全部落在技术上**（框架原理、并发、数据库、中间件、架构权衡、线上排查等），业务仅作为背景与真实性核验的载体，避免出纯业务题；**第 1 题只做概览与真实性确认，不展开具体实现细节**，第 2 题起从该项目技术点与 JD 关键能力出专题题，**每题一个明确技术主题，避免与第 1 题重复**。
- 题目数量 **6 个以内（默认 6 道）**：每道都要有代表性、能区分水平，覆盖 JD 关键能力与候选人简历核心/最新技术栈即可，不求多。
- 每题问题正文中的**分问不超过 3-4 个**：把必要追问压缩到 3-4 个小问内。
- **题目来源配比：约 70% 侧重固定 JD 核心能力**（核心业务系统设计、高并发/分布式、MySQL 调优、Redis、消息队列、Spring Boot/Cloud、并发、架构权衡等，第 1 题计入此列），**约 30% 基于简历项目与技术定制**（至少含 1 道项目真实性核验 + 简历亮点技术深挖），保证在 6 题内既能快速定位技术水平，也能核验简历真实性。
- 工作簿**不打分**：不设本题打分区与分数汇总，等级由 java-evaluator 技能按回答质量与简历综合评定。
- 使用 [references/question-bank.md](references/question-bank.md) 中的题库作为覆盖面清单与出题参考。

## 新技术 / 小众技术栈出题规范

当简历涉及面试官很可能没实际用过的新技术/小众技术栈（典型：**Spring AI、WebFlux、Reactor、SseEmitter、LangChain4J、向量检索/RAG、低代码平台、Flowable 等**）时，按以下规范出题：

1. **问「实际使用中会出现的问题」，不考「源码/底层细节」**：例如问「用了 WebFlux 后接口在高峰时变慢/某个请求卡住，怎么排查」或「Mono.zip 并行调用为什么有的接口没返回」，而不是问「Reactor 调度器的内部实现」或「Spring AI 源码里的某个类怎么工作」。
2. **参考答案必须先讲「人话」**：先用一句话说清该技术是干什么的（如「WebFlux 是响应式框架，特点是线程不阻塞，一个请求等待时不占线程」），再给**可观察的现象 → 常见原因 → 排查/验证手段**，让面试官能对照候选人的回答判断。
3. **判断要点融入参考答案正文，不单列「面试官判断提示」小节**：判断要点（如「能说清现象与排查思路即可给基础分、能讲权衡踩坑给深度分」）直接写进参考答案里，方便面试官对照，但不单独输出「面试官判断提示」标题。
   - 能说清该技术在这个项目里解决了什么问题、为什么选它 → 基础分；
   - 能说出使用中常见的坑/现象（如阻塞、超时、背压、上下文丢失）并能给出排查思路 → 深度分；
   - 能结合自己的真实经历自圆其说、细节经得起追问 → 加分。
4. **判断原则**：面试官不需要自己会用该技术也能打分——重点看候选人**能否讲清业务现象、能否说出常见坑、能否举出真实经历**；候选人说「不会」但能说出合理排查思路也值得给基础分。不要因面试官不熟悉该技术而无法判断，也不要因候选人说得玄乎就轻易给高分。
5. **打分口径**：基础分看「怎么用、解决什么问题」，深度分看「为什么、坑、权衡、踩坑经验」，与常规题一致。

## 第 1 题（最近项目技术概览题）出题规范

**默认第 1 题从候选人最近一份项目经历入手**：请候选人讲清该项目整体业务流程、自己的职责，以及用到的技术栈；面试官再从候选人的回答或简历技术点中选 1-2 个关键技术点深入（如并发、事务、缓存、MQ、数据库、三方对接）。它同时承担「项目真实性核验」与「技术水平初判」的作用，但**不再单独设水平定位题、不设水平定位勾选区**，避免与后续题目重复。

### 出题要求

1. **必须定制，禁止套模板**：第 1 题基于候选人简历中**最新一份项目**设题，标题用项目名（如「第 1 题　最近项目技术概览：海尔鑫海汇票据平台」）；简历没有的项目不要出。
2. **问题正文结构**：问题正文分 2-3 个小问，不单列追问：
   - 先讲项目业务链路、你的角色与职责；
   - 再讲该项目用到的技术栈与架构（服务拆分、调用关系、数据存储）；
   - 最后说明面试官会就其中 1-2 个技术点深入追问（如「你们这个项目 Redis 用在哪些场景？有没有遇到缓存和数据库不一致？」）。
3. **技术为主**：候选人只讲业务时，面试官要主动往技术上引导（「这块具体怎么实现的？用了什么技术？为什么这么选？」）；判断以真实经历信号（具体表结构、参数、命令、踩坑过程）为优先依据。
4. **不重复**：第 1 题只做概览与真实性确认，**不展开具体技术实现细节**；第 2 题起分别从该项目技术点与固定 JD 关键能力出发出专题题，每题一个明确技术主题，避免与第 1 题内容重复。
5. **不打分、不设勾选**：第 1 题末尾**不设「水平定位」勾选区**；等级由 java-evaluator 技能在评估报告中按回答质量与简历综合评定。

### 水平判断口径（供面试官内部参考，不写入评分表）

- 讲业务链路清楚、能说清自己职责与项目技术栈 → 基础真实；
- 对面试官深入的技术点能结合自己项目讲具体实现（表/参数/命令）→ 中级；
- 能讲为什么这么选、有哪些坑与方案权衡 → 高级；
- 能讲容量评估、架构演进与量化依据 → 资深/专家。
- 判定优先看**真实经历信号**（具体数字、时间、角色、踩坑过程），其次看知识完整性；背题答出但举不出真实案例的，不评为高级以上。

## 参考答案写作规范

- 小白友好：用通俗语言解释专有名词，首次出现时用括号补一句「人话」（如「覆盖索引（查询要的列都包含在索引里，不用回表拿数据）」）；固定术语（MVCC、B+ 树、RRF 等）保留原名，不强行翻译。
- **JVM 相关面试题已停用**：实际开发中较少使用，出题时不安排 JVM（内存模型/GC/调优/堆转储等）题目，改为考察并发编程、Spring 原理、数据库、中间件、架构等更贴近开发实践的内容。
- 加粗重点匹配项：把需要重点匹配的关键词或短句用 **加粗** 标出，方便面试官对照勾分。
- 问题正文中已融入的必要追问，其答案一并写进参考答案，**不再单列追问小节**。
- 每题「得分点（评分依据）」使用 **`<details>` 折叠块**展示：`<summary>` 即为「得分点（评分依据）」标题，**块内不出现空行**（空行会让严格 CommonMark 渲染器提前结束 HTML 块、导致内容不折叠），基础得分点与深度/加分点用 **HTML 列表（`<ul>/<li>`）** 呈现。**默认收起**、点击展开。示例：
  ```html
  <details>
  <summary>得分点（评分依据）</summary>
  <ul>
  <li>基础得分点：要点1；要点2</li>
  <li>深度/加分点：要点3；要点4</li>
  </ul>
  </details>
  ```
  不要使用「块内 Markdown 列表 + 空行」的方式（部分渲染器会不折叠）。
- 标准参考答案中**不输出「面试官判断提示」与「水平定位」**；新技术/小众技术栈题的判断要点融入参考答案正文。
- **标准参考答案也使用 `<details>` 折叠块，与得分点保持一致**：`<summary>` 即「标准参考答案」标题，块内**不出现空行**，内容用 HTML 呈现（段落用 `<p>`、**加粗** 用 `<strong>` 标签代替 `**`，保证在严格 CommonMark 渲染器下也能真正折叠）。**默认收起**、点击展开。
- **参考答案中每个要点各占一行（一个 `<p>`）**：如基础层/应用层/深挖层/落地细节、问题答案、追问答案分别换行，不要堆在一大段里，保证展开后格式清晰。
- **参考答案要足够详细但通俗**：覆盖「方案要点 → 为什么/权衡 → 常见坑 → 落地细节」，用「人话」解释，避免晦涩难懂，能支撑面试官对照判断。
- **业务类问题的标准答案不要无中生有**：以简历与候选人项目事实为准，不编造简历中没有的功能、指标或技术点；简历信息不足时，参考答案给出「应考察的判断思路/核对点」，而不是虚构细节。

## 产物与目录结构

在当前工作区创建文件夹 `<候选人姓名>/`，包含：

1. `简历.md` — 原始简历内容（保留原文，便于对照）
2. `简历源文件`（可选）— 用户以附件形式发送的简历源文件（PDF/Word/Markdown 等），复制保存时**自动重命名**为 `姓名-java-工作经验-薪资范围.原扩展名`（如 `贺士倩-java-5年-11-18k.pdf`）；纯文本粘贴、无源文件时省略
3. `<姓名>-面试题与评分表.md` — 合一面试工作簿（**文件名以求职者姓名开头**，如 `贺士倩-面试题与评分表.md`）：题目（第 1 题为最近项目技术概览题）+ 参考答案 + 每题回答记录区 + 面试官结论（结构见 [assets/面试题与评分表模板.md](assets/面试题与评分表模板.md)）
4. `评估报告.md` — 由 **java-evaluator** 技能生成（本技能不生成）：整体评价、等级评定、录用建议

从 assets/ 复制模板后填充，不要改动模板中已定义的评分规则。

## 文件命名规范

简历源文件保存时统一重命名为 `姓名-java-工作经验-薪资范围.原扩展名`，评分表文件名为 `<姓名>-面试题与评分表.md`：

- **姓名**：优先取简历正文中的真实姓名（如「姓名：贺士倩」）；文件名中的姓名（如「贺士倩 5年」）仅作参考，文件名含「潘先生」等代称时以简历正文姓名为准。
- **工作经验**：取「X年」（如 `5年`），优先从文件名提取（如「5年」），缺失时从简历正文「工作年限」或工作经历起止时间推算。
- **薪资范围**：统一转为小写 k（`11-18K` → `11-18k`、`10-15K` → `10-15k`），优先从文件名提取，缺失时取简历期望薪资或用户补充信息。
- **信息缺失**：某段信息确实无法获取时，省略该段及其连接符（如 `张三-java-5年.pdf`、`张三-java-11-18k.pdf`、`张三-java.pdf`）。
- **其他**：保留原文件扩展名；文件名中不保留 `【】_空格` 等符号；评分表文件名始终以求职者姓名开头。

## 面试题与评分表.md 结构（合一文档）

文档按「提问 → 听答 → 打分 → 汇总 → 定级」的面试流程组织，面试官自上而下使用，面试结束即可完成评分：

1. **头部信息**：候选人、岗位、面试日期、出题依据
2. **候选人关键核验信息**：以**代码块文档**形式展示（第一行姓名、手机号 + 9 项核验项，无备注列），见上方「候选人关键核验信息」规范
3. **固定 JD 匹配检查**：根据简历证据自动填入匹配结果（证据列 + 结果列勾选），无对应信息时留空
4. **简历整体分析**：先对简历做整体分析，帮助面试官快速定位候选人水平——一段总结：经验年限与学历、项目真实性线索（量化指标/角色/时间线）、亮点与疑点、对候选人水平档位的预判（初级/中级/高级/资深/专家）
5. **简历技术栈整理**：按类整理简历涉及的技术栈（Java 核心 / 框架 / 数据库 / 缓存与消息 / 中间件与分布式 / 运维 DevOps / AI 新技术），便于对照出题与追问
6. **每题一个区块**：
   - **第 1 题 = 最近项目技术概览题**：请候选人讲最近一份项目的业务链路、职责与技术栈，面试官再选 1-2 个技术点深入；只做概览与真实性确认，不展开实现细节、不设水平定位勾选（详见「第 1 题（最近项目技术概览题）出题规范」）
   - **考察方向**：如「并发编程」「数据库」「系统设计」
   - **问题**：场景化提问，尽量贴合固定 JD 与候选人最新一份项目经历；**不单列追问**，必要追问融入问题正文
   - **得分点（评分依据）**：基础得分点 + 深度/加分点，作为评分对照；使用 **`<details>` 折叠块**展示（`<summary>` 即标题，**块内用 HTML `<ul>/<li>` 且不出现空行**，保证真正折叠），**默认收起**（点击展开）
   - **标准参考答案**：小白友好型完整参考答案，包含问题与已融入追问的答案；重点匹配关键词用 **加粗** 标出；**不输出「面试官判断提示」与「水平定位」**；使用 **`<details>` 折叠块**展示（与得分点一致：块内无空行、HTML `<p>/<strong>`），**默认收起**
   - **候选人回答记录**：每题区块末尾保留空白记录区，面试时录入候选人的实际回答（java-evaluator 技能读取此区，作为出评估报告的依据）
7. **面试官结论**：通过/待定/不通过勾选 + 签名栏

> 评分表**不包含**「总体评价」「维度评估」「等级评定」三个部分（这些只出现在 java-evaluator 技能生成的《评估报告.md》中）。

打分规则：**本工作簿不打分**——每题不设「本题打分区」，也没有总体评价/维度评估/等级评定三部分；等级由 java-evaluator 技能在《评估报告.md》中按回答质量与简历综合评定。勾选项：固定 JD 匹配、面试官结论使用 Markdown ToDo 复选框（- [ ]）；候选人关键核验信息使用代码块文档。题型比例建议：约 60% 场景/实践题 + 30% 原理/概念题 + 10% 开放设计题；**题目来源配比：约 70% 侧重固定 JD 核心能力 + 约 30% 基于简历项目/技术定制（含项目真实性核验）**。每题末尾保留「候选人回答记录」区，面试时录入候选人的实际回答，作为 java-evaluator 技能的输入。

## 生成后自检（必做）

生成或重新生成《<姓名>-面试题与评分表.md》后，必须校验文档结构与编号，发现异常立即修正后再交付：

1. **区块顺序**：头部信息 → 候选人关键核验信息（代码块文档）→ 固定 JD 匹配检查 → 简历整体分析 → 简历技术栈整理 → 第 1 题（最近项目技术概览题）→ 第 2 题 … 第 N 题 → 面试官结论；**无「总体评价」「维度评估」「等级评定」三部分**；
2. **题号连续**：第 1 题为最近项目技术概览题，从第 1 题开始连续编号，不跳号、不重号；
3. **完整性**：**题数 ≤6（默认 6 道）**；**题目来源配比约 70% 侧重固定 JD、约 30% 基于简历定制（含至少 1 道项目真实性/亮点核验题）**；每题都有「候选人回答记录」区；每题**无「本题打分」、无单列「追问」小节**，问题正文**分问 ≤3-4 个**；每题**得分点与标准参考答案均为 `<details>` 折叠块（默认收起、块内无空行）**；标准参考答案**每个要点各占一个 `<p>` 换行**；第 1 题**为最近项目技术概览题、不设「水平定位」勾选**；标准参考答案**无「面试官判断提示」「水平定位」**；核验信息为代码块文档（第一行含初面评级、第 9 项为学历证明，无表格、无备注列）；**包含「简历整体分析」与「简历技术栈整理」两个章节**；
4. **内容归属**：各题内容与题号一一对应，避免区块错位（如总体评价出现在题目之间、第 2 题排在第 7 题后面）。
